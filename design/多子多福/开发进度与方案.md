> 最后更新：2026-10-14
> 用途：脱离代码也能读懂当前状态与设计决策，便于在无编程环境时讨论、修改方案。
> 配套：同目录下的 `模块*.md` 是**原始设计文档**，本文档记录**实际实现与原始设计的差异**。

# 一、项目背景

基于开源项目 **`setube/vue-idle-xiuxian`**（MIT，Vue 3 + Vite + Pinia + Naive UI 的浏览器端放置修仙游戏）二次开发，改造为小说《多子多福：开创仙朝》主题。

**仓库状态**
- 改造在新分支 `duoziduofu` 上，`main` 保持上游原样
- 打了 tag `upstream-v1.0.5` 锚定上游原始状态
- 远端仍指向上游作者仓库，**尚未推送**，也没有自己的远端
- git 身份只做了仓库级配置（未污染全局）

**目录约定**
| 路径 | 用途 |
|---|---|
| `design/多子多福/` | 设计资料（原设计方案 md、小说原文、素材表）。**注意原在 `docs/`，已迁出** —— 那是 `vite build` 的输出目录，`emptyOutDir` 默认开启，放那里下次构建会被清空 |
| `src/stores/modules/` | 拆分后的 store 模块，每个模块一个文件 |
| `src/plugins/` | 纯数据 / 纯函数模块（不依赖 Vue） |

**技术约定**（新增模块时遵守）
- store 用**单 Pinia store + 按模块拆文件**，对外仍是同一个 `usePlayerStore()`，视图层零改动
- 每个 store 模块导出 `state()`（**必须是工厂函数**，`$reset` 依赖）、`getters`、`actions`
- actions / getters 用方法简写，**不能用箭头函数**（否则跨模块的 `this.xxx()` 会断）
- 模块内禁止 `import { usePlayerStore }`（循环依赖），跨模块一律走 `this.xxx`
- 存档自动纳入：`saveData()` 序列化整个 state，读档时 `deepMerge` 合并（对象递归、**数组整体替换**）

# 二、素材出处的两个重要澄清

## 1. 那份物品素材表 `zml_huiji_dataV7.xlsx` 不是《多子多福》的

它是 **《修真门派掌门路》**（`zml` = 掌门路）的 wiki 物品库，共 15 个 sheet（灵植/丹药/法阵/符篆/灵兽/灵材/灵食/尸鬼/炼术/书籍/法器/势力/灵地/功法/人物），内容全是 齐休 / 楚秦门 / 齐云派 / 白山 / 南疆。

在它里面检索 `飞鹰|长岭|桂冈|洪晃|萧家|郑家`：**0 命中**。

**结论**：它只共享**术语体系**（灵根、本命、练气→筑基→金丹、法器一至六阶·下中上极），地理势力与《多子多福》完全不重叠。**当通用素材池用**（丹方、灵草、法器名目、品阶模板），地名人物不能照搬。

## 2. 「同参」一词在小说原文里一次都没出现

小说原文用的是「本命之物」「符合本命的随身之物」。「同参」是从《修真门派掌门路》借来的术语。

书友圈共识：**《多子多福》属于修仙末世设定，传承断绝，同参这个概念名已经失传，但功效仍在**。

**当前决定：游戏内 UI 照用「同参」二字**，不做世界观自圆。

# 六、模块一「修行与突破」设计（已实现）

## 核心循环
```
四维契合度 → 决定灵力积累速度（速度线）
           → 决定能否冲击门槛节点（门槛线）
挂机自动累积：功法熟练度 / 同参祭炼
上线操作：切换功法/同参/灵地、打坐、突破、散功重修
```

## 四维契合度公式（实际实现）

```
综合契合度 = (功法契合 + 同参契合 + 灵地契合 + 本命契合) / 4     每维归一到 [0,1]
```

| 维度 | 公式 | 匹配对象 |
|---|---|---|
| **功法契合** | 五行基础分 + 功法等级 × 2% + 熟练度 | 与**本命**的五行关系 |
| **同参契合** | 五行基础分 + 同参等级 × 3% + 祭炼 | 与**本命**的五行关系 |
| **灵地契合** | 灵地等级系数 × (1 + 五行匹配系数) | 与**活跃功法**的五行关系 |
| **本命契合** | 境界系数 + 本命技数 × 10% + 本命物数 × 5% (+共鸣 15%) | — |

**五行系数表**

| 关系 | 功法 | 同参 | 灵地 |
|---|---|---|---|
| 相生 | +40% | +50% | +30% |
| 相同 | +30% | +40% | +20% |
| 相克 | −10% | −20% | −10% |

> **方向性已刻意做成同权** —— `A生B` 与 `B生A` 加成相同。理由：契合度衡量的是「搭不搭」而不是「谁养谁」，拆方向权只增加玩家理解成本、不增加策略深度。代码里保留了方向字段，将来若想拆权，只改常量不用改公式。

**境界系数**（本命维）：练气 0.5 / 筑基 0.8 / 结丹 1.0

**灵地等级系数**：一阶下品 0.5 / 一阶中品 0.7 / 一阶上品 0.9 / 二阶下品 1.0 / 二阶中品 1.2 / 三阶 1.5

## 修炼速度

```
灵力/秒 = 基础 × spiritRate × (0.5 + 综合契合度 × 1.5) × 重修补偿
```
契合度 0% → **半速**，50% → 1 倍，100% → **双倍**。

**实测开局数值**：功法 42.0% / 同参 53.0% / 灵地 65.0% / 本命 75.0% → **综合 58.8%**，速度倍率 **1.38×**。

## 熟练度 / 祭炼的节奏

原始设计文档写「每 100 小时 +1%」，但游戏里 1 tick = 1 秒，不可玩。重新标定：把「游戏小时」当抽象单位，设 `secondsPerGameHour = 2`（现实 2 秒 = 1 游戏小时）。

| 项 | 累积速度 | 上限 | 满值耗时 |
|---|---|---|---|
| 功法熟练度 | 每 100 游戏小时 +1% | 20% | 约 67 分钟 |
| 同参祭炼 | 每 50 游戏小时 +2% | 20% | 约 17 分钟 |

**存原始秒数而不是百分点** —— 调参立即生效，不需要迁移存档。调试期把 `secondsPerGameHour` 设 0.1 可快 20 倍。

## 功法分品阶（**这是对原始设计的修正**）

| 品阶 | 层数上限 | 功法契合上限 |
|---|---|---|
| 练气篇 | 10 | 0.40 + 0.20 + 0.20 = **80%** |
| 筑基级 | 15 | 0.40 + 0.30 + 0.20 = **90%** |
| 金丹级 | 20 | 0.40 + 0.40 + 0.20 = **100%** ✓ |

## 外功（炼体）

- **不设契合度门槛** —— 纯水磨。设计意图：内功被门槛卡住时，炼体是一条始终可推进的路
- 打坐可切换「修内功 / 修外功」，共用同一套灵力消耗
- 炼体提供**生命 / 防御**加成，随外功境界增长（1 级 生命+21/防御+2 → 18 级 生命+720/防御+72）
- 加成走**派生值**（`totalHealth` / `totalDefense`）而**不写进本体属性** —— 现有装备/灵宠加成都是双向增量加减、已有漂移风险，派生值没有任何写操作，物理上不可能漂移

## 散功重修（最小可行版）

**代价**：清空灵力与内功修为、境界回到练气一层、功法熟练度与同参祭炼各减半
**收益**：每次重修永久获得 —— 修炼速度 ×(1+次数)、灵力获取 +(10%×次数)
**外功不受影响**

# 七、对原始设计文档的修正（重要）

实现过程中发现原始设计文档有**三处数值/公式错误**，已修正：

## ① 「本命契合」公式量纲不成立
原文：`本命契合 = 境界系数 × 本命技解锁数 × 本命物收集数`
- 解锁数是**计数**，乘法会让没有本命技时整维归零
- 练气期两技两物会得到 `0.5 × 2 × 2 = 2.0`（200%），筑基期更高
- 文档自己的示例（练气期 55%）用乘法凑不出来

**改为加性**，与另外三维「基础分 + 百分点加成」的口径一致：
`境界系数 + 本命技数×10% + 本命物数×5% (+ 共鸣 15%)`

## ② 结丹门槛（100%）按原文数值永远达不到
按原文推演四维上限：功法 80% / 同参 100% / 灵地 100% / 本命 100%
→ `综合上限 = (0.8+1+1+1)/4 = 95%` —— **卡死在 95%，结丹永远突破不了**

**修正**：功法分品阶、层数上限随品阶放开（见上表）。金丹级功法满配恰好 100%，门槛可达。

> ⚠ 注意：这个可达性依赖「有一本金丹级且五行相合的功法」。**如果后续重做同参/本命系统，务必重新验证结丹门槛仍然可达。**

## ③ 熟练度节奏不可玩
「每 100 小时 +1%」在 1 tick = 1 秒的游戏里等于 100 现实小时涨 1%。已按上表重新标定。

# 八、已知问题 / 待决策

## 🔴 待重做：功法与同参的五行选择没有区分度

**现象**：三本功法的契合度全是 **42.0%**，五个同参全是 **53.0%**。玩家选哪个都一样，五行系统形同虚设。

**原因**：当前实现是「对全部本命取最大值」。玩家有火、土两个本命，而它们在五行里互为相生（火生土），于是几乎任何属性都能跟其中之一凑出「相生」拿满分。

**曾尝试的修法**（已撤回）：给本命加角色配对 —— 功法对着「本命兽·刃背乌鬣猪」评、同参对着「本命物·饕餮纹玉牌」评。这与原始设计文档两张表的写法一致（功法表逐行对着乌鬣猪、同参表逐行对着玉牌）。撤回是因为**用户确认这块设计后续会推翻重做**，不要现在修。

**重做时的约束**：必须同时保住「结丹门槛 100% 可达」。

**代码位置提示**：问题写在 `src/plugins/cultivationData.js` 的 `PLAYER_FATES` 上方、`src/plugins/harmony.js` 的 `bestFateMatch` 上方。

## 🟡 本命维开局即饱和
本命契合开局就有 75%，到筑基阶段就顶到 100%，几乎没有成长空间。这是「让结丹门槛在本轮就可达」的必然结果（境界系数必须够高才能把本命顶到 1.0）。等模块二接入更多本命技/本命物来源后可重新配平。

## 🟡 没有离线收益
代码里没有 `lastSaveTime` 或任何时间差补偿。关掉页面进度就停住，回游戏不会补算。对应原始设计文档的**模块九·离线结算**，尚未实现。

## 🟡 每秒整包存档
`gainSpirit` 每秒被调用一次，结尾都 `saveData()` —— 每秒把整个 state 加密写一次 IndexedDB，比较重。上游有过一个「修复内存溢出问题」的提交。可考虑加节流。

## 🟡 成就系统里有三个字段名对不上
`achievements.js` 引用了三个 store 上**不存在**的字段，导致「装备 / 秘境连杀 / 高阶炼丹」三类成就永远无法达成（有可选链兜底，不会报错，属静默失效）：
- `player.equipment` → 应为 `Object.values(equippedArtifacts)`（注意它是对象不是数组）
- `player.dungeonStreakKills`、`player.highQualityPillsCrafted` → 无对应字段

未修，因为成就要被新模块替换。

- `Dockerfile` **是个坑** —— 它不构建本地代码，而是 `git clone` 上游仓库再 build，打出来的镜像跑的是上游原版。`docker-compose.yml` 同理（直接拉上游镜像）
- `README.md` 仍是上游项目介绍

# 九、后续模块排序建议

原始设计文档给的依赖关系大致是：修行 → 子嗣（加成）→ 内宅（孕育）→ 封地（资源）→ 任务 → 经济 → 事件 → 离线。

**我当时建议的 MVP 顺序**：

| 顺序 | 模块 | 理由 |
|---|---|---|
| 1 | ✅ 修行与突破 | 已完成。且子嗣给的加成是作用在**修炼速度**上的，这条线做完子嗣才有意义 |
| 2 | 内宅姻缘 | 子嗣的**来源** —— 没有侍妾就没有子嗣。精力系统、好感度、怀孕判定 |
| 3 | 多子多福 | 游戏的招牌。子嗣抽卡、灵根、本命、词条、人口基数 → 灵根概率的正循环 |
| 4 | 封地经营 | 资源产出引擎，给内宅和修行提供消耗品 |
| 5 | 任务战斗 | 派遣子嗣，产出贡献与战利品 |
| 6 | 经济交易 | **必须在封地/任务之后** —— 经济是回收系统，产出端没上线就做回收没有意义 |
| 7 | 事件叙事 / 百艺科技 / 离线结算 | 粘合剂与闭环，放最后 |
| — | 门派政治 | 废案 |

> 内宅与多子多福耦合很紧（侍妾→怀孕→子嗣诞生→抽卡），建议**当成一期一起做**。

# 十、改方案时的调参入口

如果要在网页端讨论数值改动，主要改这几个地方：

| 想改什么 | 改哪里 |
|---|---|
| 契合度公式、五行系数、修炼速度倍率、熟练度节奏、炼体加成量 | `src/plugins/harmony.js` 顶部的 `TUNING` 常量块 |
| 境界表、修为曲线、门槛位置 | `src/plugins/realm.js` |
| 功法 / 同参 / 灵地 / 本命的数据与数值 | `src/plugins/cultivationData.js` |
| 修炼消耗与收益曲线 | `src/plugins/cultivationMath.js` |
| 五行相生相克关系 | `src/plugins/wuxing.js` |

**注意**：`POWER_LEVEL_SCALE = 7`（在 `realm.js`）是对「境界表从 126 级压缩到 18 级」的补偿系数，只作用于**幅度**（装备属性、丹药效果、事件奖励），**绝不能用在等级门槛判定上** —— 那会让穿戴/突破门槛永久锁死。

# 十一、验证手段（没有测试框架）

三层兜底，前两层自动化、第三层需人工：

1. **纯函数断言** —— `wuxing.js` / `harmony.js` / `cultivationData.js` / `cultivationMath.js` 都无浏览器依赖，可直接用 node 断言
2. **headless store 探针** —— 本机没有 headless 浏览器，但可以在 node 里用 Pinia 真实实例化 store：把源码复制到临时目录、给相对 import 补 `.js` 扩展名、把 `import.meta.env.DEV` 置 false、存根 `localStorage` 并置空 `saveData`。模块一的 **37 项运行时断言**就是这么跑的（门槛拦截、结丹突破、炼体派生、散功重修、`$reset` 无共享引用等）
3. **浏览器冒烟** —— `npm run dev`（端口 2025），人工点验。重点：修行页雷达图、切换配置后数值立即变化、门槛拦截提示、外功进度
