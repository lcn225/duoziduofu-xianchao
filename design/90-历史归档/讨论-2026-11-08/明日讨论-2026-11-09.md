## A 类：不定就没法开工

### A1. 金丹期（168×）还逐日结算「桂冈的一天」吗？体力 / 精力还要不要算？

**现状**

**① 时间有多快**

- 金丹 **168×**：1 现实秒 = **42 游戏小时 = 1.75 游戏天**；1 游戏天 = **0.571 现实秒**
  （《时间系统》§2.1 ③）。
- 换算到常用单位：1 游戏周 = **4 现实秒**、1 游戏月 = **17.1 现实秒**、
  1 游戏年 = **3.48 现实分钟**。

**② 引擎在做什么**

- 时钟每 **1 现实秒**一个 tick；每个 tick 调一次 `advanceDayLoop`，内部逐日跑 `stepDay`。
  金丹下一次 tick 要结算 **1.75 个游戏天**。
- 已知性能账（R34，未做聚合引擎）：金丹 **day 钩子 1.75 次/现实秒**、
  **hour 钩子 42 次/现实秒**，日结实测约 **77 ms/tick**。
- 在线与离线走的是**同一条** `stepDay` 路径；离线重放也是逐日跑，没有第二套公式。

**③ 玩家看得到什么**

- 筑基后小循环已退到 **UI 层**：Day 页只留「昨日战报」+ 策略设置，不再显示实时任务卡 / 流水账。
- 金丹下「昨日」= **0.571 秒前**，战报每秒被刷新约 **1.75 次** —— 数字在动，但读不出来。
- 内宅已经改成**游戏周周报**（7 游戏天 = 4 现实秒一条），比战报可读，但仍然偏快。

**④ 桂冈的体力 / 精力现在还在约束产出**

- 体力上限 = **145 + 外功加成**，洗髓十层 = **232**；精力上限固定 **100**。
- 睡觉恢复体力 = **上限 / 4 每小时**（232 → 58/h，**4 小时回满**）；
  精力：睡觉 +5/h、练功 +10/h。
- **体力决定晚间互动次数**：互动 **15 体力 / 次、0.5h**，且要留 `fatigueThreshold = 30`
  不花（`(体力 − 30) / 15`）。145 体力开局挑 **7 人**；232 体力约 **13 人**。
  一晚 12 小时在时间上最多 24 次 ⇒ **体力是瓶颈，不是时间**。
- **精力决定白天能做几门百艺**：每门每天扣一次（炼丹 / 制符 30、炼阵 / 炼器 35）；
  精力归零会**提前下班**。4 门 = 130 > 100，要靠练功的 +10/h 补贴才撑得住。
- ⇒ **删掉体力 / 精力不是纯展示改动**：互动次数、有喜概率、练功小时、百艺产出都会变。

**要定的分叉**

1. **保留逐日引擎，只改展示**：金丹 Day 页把「昨日战报」换成**游戏月汇总**；
   体力 / 精力照算。R34 聚合引擎只优化实现，不改规则。
2. **金丹起关掉体力 / 精力**：桂冈视为满状态，日循环只按时间排。
   好处是少两个状态；代价是互动 / 百艺 / 怀孕产出全变，且与离线逐日重放分叉。
3. **金丹起粗结算**（一次算 7 / 30 天）：材料耗尽、仓满、寿终、怀孕、突破都是**路径相关**的，
   粗结算要么内部还是逐日跑（等于没省），要么引入近似（和离线分叉）。
4. **金丹起「桂冈闭关」**：跳过日循环，直接给修炼 / 百艺的月收益，多子多福与封地另算。
   这是**新玩法**，不是结算粒度调整。

**建议**

- **选 1。** 理由三条：
  1. **只有一条路**：逐日 `stepDay` 是在线 / 离线唯一共用路径。另写一份「金丹聚合」必然与离线分叉，
     这正是 CLAUDE.md 已经写死的硬规矩（「别再写一套按游戏日聚合的日终结算」）。
  2. **体力 / 精力仍在真实约束**：金丹下互动约 13 人（时间上限 24）、百艺 3 门（4 门吃满 130 精力），
     删掉会直接改产出，要重登《产出登记表》并重算怀孕 / 子嗣节奏。
  3. **真正的问题是「展示」和「性能」**，不是语义：
     - 展示：金丹 Day 页改**游戏月汇总**（17.1 现实秒/期，读得出来）。
     - 性能 / 离线上限：走 **R34 聚合引擎**（离线 1,500 → 目标 30,240 游戏天），只换实现、不改规则。
- 如果你的本意是「金丹期不该再过日常」，那是 **4**，属于新玩法，**单独立项**，
  不要混在结算优化里顺手做。

**影响**

- 选 1：纯 UI，**0 断言**；R34 另算（性能工程，1~2 会话）。
- 选 2 / 3：改引擎 + 老档迁移 + **20~40 条断言**，还要重登《产出登记表》。
- 选 4：新玩法，单独立项。

### A2. 金丹期的展示单位：日 / 周 / 月 / 年？

**现状**

- 练气期：Day 页实时卡片 + 流水账，**日**为单位。
- 筑基后：Day 页「昨日战报」，**日**为单位（1 天 = 4 现实秒）。
- 内宅：筑基后已改**游戏周周报**（1 周 = 4 秒 / 筑基 28 秒）。
- 俸禄：练气按月发、筑基后按游戏年发（金丹 1 年 = 3.48 现实分钟）。

**要定的分叉**

1. 金丹 Day 页显示 **周报 / 月报 / 年报** 哪一档？
2. 内宅周报在金丹要不要也抬成**月报**（4 秒/期 → 17.1 秒/期）？
3. 俸禄 / 封地税收 / 探索收益这些「已经按游戏月 / 年结算」的，要不要在 UI 上统一口径？

**建议**

- **按段分档：练气 = 日报、筑基 = 周报、金丹 = 月报。**
  金丹一个月 17.1 现实秒，正好是「一眼能读完、又不会每秒刷新」的粒度；
  年报 3.48 分钟太稀，会漏掉中间的异常（材料耗尽、仓满、寿终）。
- 内宅在金丹也改月报，和 Day 页同一个节拍；练气期继续看实时流水。
- 这是**展示层分档**，不改任何结算。实现上只是换 `periodSummary` 的窗口长度。

**影响**：纯 UI，**0 断言**；1 个会话（Day 页 + 内宅页两处汇总组件复用）。

**出处**：[《当前实现》§四 8d](../../00-总览与状态/当前实现.md) ·
[《时间系统》§2.1 ③](../../20-系统设计/时间系统.md) · 《模块二》§7.4。

## B 类：开工前一周定

### B1. R34 聚合引擎的范围：只做离线，还是在线金丹也走聚合？

**现状**

- 离线配额现在落到**过渡值 1,500 游戏天**（金丹 = **14.3 现实分钟**），
  目标态 **30,240 游戏天 = 4.8 现实小时**；差距只能靠 R34 聚合引擎补。
- 在线金丹：**77 ms/tick**（1 tick/秒），可接受但已是已知性能债；
  日钩子 1.75 次/秒、小时钩子 42 次/秒，都在 `checkBoundary` 里逐步补触发。

**要定的分叉**

1. R34 只做离线重放（把 30,240 天压进 60 秒），在线继续逐日？
2. 在线也做聚合（比如金丹只结算「每游戏月」的代表日）？

**建议**

- **先只做离线。** 在线的 77 ms/tick 还没到玩家可感知的卡顿；
  而离线是「一次要算几年」，必须聚合。在线若也聚合，就会和 A1 的「唯一路径」原则冲突，
  而且在线本来就没有「一次算 30,240 天」的需求。
- R34 的验收口径不变：**离线结算 ≤ 60 秒**，抬到目标态后只改
  `OFFLINE_TUNING.maxGameDays` 两个常量。

**影响**：性能工程，1~2 会话；不改规则、不新增断言（现有离线断言要保证不回归）。

[《下一步》新待办 2026-11-03 #1](../../00-总览与状态/下一步.md) · 《产出登记表》R33 / R34。

## C 类：边做边定

### C1. 互动成本：设计值 20 体力 / 1h，代码值 15 体力 / 0.5h，要不要统一？

**现状**

- 《当前实现》§四明确标着「互动成本：设计 **体力 20、1h、18:00** / 实现 **体力 15、0.5h、20:00**，
  ⬜ 未返工」。
- 代码里 `fatigueThreshold = 30` 的注释也写着：「互动成本 15→20、0.5h→1h 那批一起返工时再决定是否删」。
- 两条值直接影响 **A1 的结论**：如果金丹保留体力 / 精力，这个数字就是「一晚几次」的分母。

**建议**

- **保留现状（15 / 0.5h），把设计文档改成现状。** 理由：
  20 / 1h 会把 232 体力的互动上限从约 **13 次**降到约 **10 次**，一晚时间上限也从 24 降到 12；
  两条同时收紧，子嗣节奏要重新标定。现在没有非改不可的理由。
- 如果 A1 最终选「关掉体力 / 精力」，这条**自动消失**，不用单独处理。

**影响**：改则 1 条 TUNING + 若干断言；不改则只改《当前实现》/《日常循环》的一行口径。
