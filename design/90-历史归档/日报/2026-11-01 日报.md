## 七、秘境整备页：名单分页 + 卡顿修复

**起因**：用户反馈「整备页极卡」，同时要求「子嗣与灵宠不用显示那么多人，每页 10 人，兼顾排序」，
并指定先砍显示人数、看他之后还卡不卡。**分页后实测仍卡** ⇒ 瓶颈不在渲染条数。

**第一步 · 分页**（`views/Dungeon.vue`）

- 子嗣、灵宠两块名单都改成每页 10 条，`n-pagination` 跟在勾选列表下面，
  超过 10 条才出现，右侧带「共 N 人 / 共 N 只」。
- **排序是全局的**：先按当前排序（子嗣 战力/境界/灵根，灵宠 战力/等级/成色）排完再切页，
  第 1 页永远是「当前排序下最靠前的 10 个」。
- 勾选状态本来就按 id 存在 `draftOffspringIds` / `draftPetIds` 里，**跨页不丢**；
  换排序 / 名单变短时自动回第 1 页。

**第二步 · 卡顿根因**（分页救不了的原因）

```
clockGameTime 每 tick 变
  → secretRealm.adultOffspringCandidates（读 this.clockGameTime）返回新数组
  → Dungeon.powerRows 重算：每个候选中嗣 buildOffspringUnit（含装备面板合并）+ 每只灵宠 buildPetUnit
  → sortedOffspring 用 powerOf 重排一遍
```

关键在于**秘境页不在 `PAUSE_ROUTES` 里**（`stores/modules/clock.js:48`），时钟一直在走；
而这段成本**只跟候选总数有关，与显示条数无关**。附带一条讽刺：`canFightOf(child, nowGameSeconds)`
的第二个参数**根本没用到**（`innerCourt.js:1941` 只判 status / hasRoot / realmLevel），
这个时钟依赖纯属白烧。

**修法**

| 文件 | 改动 |
|---|---|
| `plugins/secretRealm.js` | 新增 `adultCandidatesOf(list, nowSeconds)` —— filter 抽成唯一真源，store getter 与整备页共用 |
| `stores/modules/secretRealm.js` | `adultOffspringCandidates` 转发 `adultCandidatesOf`（行为不变）；删掉随之不再使用的 `canFight` import |
| `views/Dungeon.vue` | 新增 `listNow` = **按游戏天刷新**的时钟快照；候选名单 / `powerRows` / `growthText` 全读快照，不读实时时钟 |

效果：`powerRows` 从「每 tick 一次」降到「每游戏天一次」（练气 96 现实秒、筑基 4 现实秒）。
**用户实测：好多了。**

**坑已入库**：开发手册 坑列表新增 **#18「在 computed / 模板里读实时时钟 = 每 tick 全量重算」**，
含「卡顿与列表长度无关 ⇒ 先查 computed 的 tick 依赖」这条判断法。

   **一整天一点经验都不产生**。用户在追问里确认「挂的是探索/秘境」，对上了。
3. **就算回镇守也很慢**：灵兽 `L→L+1` 需求 = **自己那层**修为上限 × 2、只拿打坐修为的 50%

   以筑基五层每次打坐 12 修为计，约 **2,200 次打坐 ≈ 640 万灵力**，是主角自己升一级
   （~850 次 / 250 万灵力）的 2.5 倍。
4. **离线再打折**：筑基期离线仍按 **180 游戏天**封顶（`offlineSimulation.js:49`，R33 待办），

## 十二、B9-b `K(L)` 进代码（P56-d，理想曲线口径）

**起因**：B9-b 卡了一整天。P56-b 重标出来的 `K` 表里，**L20（筑基十层）的 K = 4.419**

**口径（`npm run sim:k -- --ideal`）**

1. **练气段照搬锚点摊法的结果**（那一段已经定死，一个字没动）。
2. 从**练气十层的填满耗时 10,740 秒**起，L11~L29 走**一条等比线**，比值由
   「终点精确落在金丹十层累计 682,560 秒」反解 ⇒ **r = 1.10691**。
3. 每级耗时**严格递增、零台阶**；逐级 `K = 目标 ÷ 裸耗时`，不再有「分段 K」。

**为什么分段 K 是错的**（不是推导错，是假设不成立）：分段 K 隐含「同一区间内每级时间 ∝ 裸耗时」，
而裸耗时在境界边界会跳水 —— 修为/秒从练气十层 **0.73** 跳到筑基一层 **1.61（×2.2）**，
`Base_Exp` 只涨 7%。常数 K 于是必然让「筑基一层」比「练气十层」还快。这个假设只在
「一段 = 一格」（18 级时代）时成立。

**审计：四条锚点摆到曲线上，20 / 21 改判**

| 锚点 | 宪法原值 | 理想累计 | 偏差 |

| **金丹一层** | 57.0h | **62.1h** | 早 5.11h · 9.0% |
| 金丹十层 | 189.6h | 189.6h | 贴合（曲线终点） |

> 33 小时是 18 级时代「筑基圆满」那格的残留（当年后面紧跟 32 小时的结丹初期，所以不刺眼）；
> P61 切成 10 级后，后面变成 6.7 小时的第一格，支撑消失。而且 33 小时一旦保留，
> 筑基段后九格只能压在 25.3 小时里（均 **2.81h/级 < 练气十层的 2.98h**），直接违反「每级越长」。

**形状是坏的**：练气段本来就对得上，但筑基之后外功「几分钟走完一段」——
根因只有一个：**24×**。同样「5 轮/游戏天」，练气占 96 现实秒、筑基后只占 **4 现实秒**，
外功按现实时间看产出快 24 倍，而门槛还是裸 `Base_Exp`。内功早就用 `INNER_PACE` 处理过这件事，
外功一直挂着（《真值表》§2.4c 第 4 条明写「已知缺口」）。

**改动（用户拍板：与内功同级同耗时 / 18→30 级残留走 `powerLevelOf`）**

| 件 | 内容 |
|---|---|
| `realm.js` | 新增 **`OUTER_PACE`**：`PACE = 5 轮/天 × gain × 内功目标天数`（每游戏天 96 / 4 现实秒）。逐级单调，L1 81 → L30 1,330,713 |
| `bath.js` | `BATH_PARAMS` **18 → 30 行**、`BATH_MAX_LEVEL = 30`。旧锻骨四档落在 11/14/17/20、洗髓四档落在 21/24/27/30，中间六格线性插值；**练气 10 行没动** |

| `innerCourt.energyMaxOf` | 同上 —— 否则 L19+ 掉进已删的「超级炼体 +25」档，体力上限 532 |

**三条硬口径**

1. **`gain` 不决定节奏**：门槛里自带 `5 × gain`，改 gain 只把进度条数字一起放缩（每轮仍 `+gain`）。
   真正的旋钮是 `OUTER_PACE`。改 `BATH_PARAMS.gain` 或内功 PACE **必跑 `npm run sim:body`**。
2. **段总量守恒仍读 `baseExp`**（外功 17,680 / 116,000 / 576,000），PACE 不进守恒。
3. **练气段几乎不动**（7.58h → 7.70h）—— 外功曲线「同构、低两成」和 96 秒/天两个因子互相抵消，
   变化全落在筑基之后。
