# 一、项目背景

基于开源项目 **`setube/vue-idle-xiuxian`**（MIT，Vue 3 + Vite + Pinia + Naive UI 的浏览器端放置修仙游戏）二次开发，改造为小说《多子多福：开创仙朝》主题。

**仓库状态**
- 改造在新分支 `duoziduofu` 上，`main` 保持上游原样
- 打了 tag `upstream-v1.0.5` 锚定上游原始状态
- 远端仍指向上游作者仓库，**尚未推送**，也没有自己的远端
- git 身份只做了仓库级配置（未污染全局）

**目录约定**
| 路径 | 用途 |
|---|---|
| `design/多子多福/` | 设计资料（原设计方案 md、小说原文、素材表）。**注意原在 `docs/`，已迁出** —— 那是 `vite build` 的输出目录，`emptyOutDir` 默认开启，放那里下次构建会被清空 |
| `src/stores/modules/` | 拆分后的 store 模块，每个模块一个文件 |
| `src/plugins/` | 纯数据 / 纯函数模块（不依赖 Vue） |

**技术约定**（新增模块时遵守）
- store 用**单 Pinia store + 按模块拆文件**，对外仍是同一个 `usePlayerStore()`，视图层零改动
- 每个 store 模块导出 `state()`（**必须是工厂函数**，`$reset` 依赖）、`getters`、`actions`
- actions / getters 用方法简写，**不能用箭头函数**（否则跨模块的 `this.xxx()` 会断）
- 模块内禁止 `import { usePlayerStore }`（循环依赖），跨模块一律走 `this.xxx`
- 存档自动纳入：`saveData()` 序列化整个 state，读档时 `deepMerge` 合并（对象递归、**数组整体替换**）

# 二、素材出处的两个重要澄清

## 1. 那份物品素材表 `zml_huiji_dataV7.xlsx` 不是《多子多福》的

它是 **《修真门派掌门路》**（`zml` = 掌门路）的 wiki 物品库，共 15 个 sheet（灵植/丹药/法阵/符篆/灵兽/灵材/灵食/尸鬼/炼术/书籍/法器/势力/灵地/功法/人物），内容全是 齐休 / 楚秦门 / 齐云派 / 白山 / 南疆。

在它里面检索 `飞鹰|长岭|桂冈|洪晃|萧家|郑家`：**0 命中**。

**结论**：它只共享**术语体系**（灵根、本命、练气→筑基→金丹、法器一至六阶·下中上极），地理势力与《多子多福》完全不重叠。**当通用素材池用**（丹方、灵草、法器名目、品阶模板），地名人物不能照搬。

## 2. 「同参」一词在小说原文里一次都没出现

小说原文用的是「本命之物」「符合本命的随身之物」。「同参」是从《修真门派掌门路》借来的术语。

书友圈共识：**《多子多福》属于修仙末世设定，传承断绝，同参这个概念名已经失传，但功效仍在**。

**当前决定：游戏内 UI 照用「同参」二字**，不做世界观自圆。

# 六、模块一「修行与突破」设计（已实现）

> **本节的公式已于 2026-10-15 按《[灵气系统 — 最终设计文档](../../10-模块设计/模块一-修行与突破.md)》整体重做。** 旧版（等权四维、`0.5 + 契合×1.5`、五行相生相克、同参带等级与祭炼）已全部作废。
>
> 数值有机器可读的断言：`npm run verify`（**234 条**：契合度 + 模块二，见 `scripts/verify-harmony.mjs`）。

## 核心循环
```
四维契合度（加权） → 决定能否冲击门槛节点（门槛线）
                   → 以 0.7×~1.3× 的弱倍率影响速度（不是收益引擎）
灵地基础产出       → 决定灵力积累的基数（速度线）
挂机自动累积：功法熟练度
上线操作：切换功法/同参/灵地、打坐、突破、散功重修
```

## 灵气类型（7 类）

五行（金木水火土）+ 特殊（**兽**、**器**）。**本命决定灵根**：

| 本命类型 | 灵根 |
|---|---|
| 灵兽 / 妖兽 | 兽 |
| 器物 / 法器 | 器 |
| 草/木/花、火/炎/焰、水/冰/液、土/石/山、金/铁/矿 | 对应的五行灵根 |

> 武器是**器**灵根，不是金灵根。
> 兽 / 器 与五行之间**没有**相生相克关系 —— 新契合度也不用五行关系，改用「覆盖率」。

## 三维契合度公式（实际实现）

```
综合契合度 = 功法 × 0.15 + 同参 × 0.50 + 灵地 × 0.35     每维归一到 [0,1]
```

| 维度 | 权重 | 公式 |
|---|---|---|
| **同参契合** | 0.50 | 接近度系数（正主 1.0 / 同系列 0.7 / 同类型 0.4 / 无关 0.15）× **min(同参品阶系数, 本命品阶系数)** |
| **灵地契合** | 0.35 | 匹配百分比（纯属性匹配，**与灵地等级无关**） |
| **功法契合** | 0.15 | 品阶分（练气篇 20% / 筑基级 30% / 金丹级 40%）+ 覆盖率 × 40% + 熟练度 |

> **「本命契合」这一维已整维删除。** 它是随境界自动上涨的常数（练气 75% → 筑基自动满值），
> 白送 26.25 个点且玩家经营不了。本命现在只通过两件事起作用：决定灵根（灵气属性）、
> 以及用**本命品阶**封顶同参契合。
>
> ⚠ 桂冈两个本命都是**四阶**，`min(同参品阶, 1.00) = 同参品阶` —— 这个封顶对他是惰性的，
> 只在低阶本命的角色身上生效。

**两个「覆盖率」的分母刻意不同**（这是设计要点，别把两个函数合并）：

```
功法覆盖率 = |功法灵气 ∩ 修士灵气| / |修士灵气|     ← 分母是修士
灵地匹配度 = Σ 灵地灵气[e] 其中 e ∈ 修士灵气        ← 分母是灵地
```

桂冈（兽 + 器）为例：兽吼功（兽）覆盖 1/2 = 50% → 20%；兽器双修经（兽+器）100% → 40%；开局三本（火/土/金）0% → 0%。
快子峰顶木屋（兽 60% + 器 40%）匹配 100%；郑家山门核心（木 100%）匹配 0%。

**品阶系数**（同参与本命**共用同一张表**）：不入品 0.20 / 一阶下品 0.30 / 一阶中品 0.35 / 一阶上品 0.40 / 二阶 0.55 / 三阶 0.75 / 四阶 1.00

## 修炼速度

```
灵力/秒 = 灵地基础产出 × (0.7 + 综合契合度 × 0.6)
        × spiritRate × 本命数量系数 × 行功带宽 × (1 + 子嗣修炼加成)
```

| 系数 | 说明 |
|---|---|
| 灵地基础产出 | 一阶下品 1.0 / 一阶中品 1.5 / 一阶上品 2.0 / 二阶下品 3.0 / 二阶中品 4.0 / 三阶 7.0 / 四阶 10.0 / 五阶 15.0 |
| 契合度项 | **0% → 0.70×，100% → 1.30×**（跨度只有 1.86 倍） |
| spiritRate | 每次内功突破 ×1.2 |
| 本命数量系数 | 单本命 1.0 / 双本命单灵根 0.9 / 双本命双灵根 0.8 / 三本命 0.7 / 三本命以上 0.6 |
| 行功带宽 | **占位，恒 1.0** —— 五种散功 + 边际衰减 + 上限尚未实现 |
| 子嗣修炼加成 | ✅ 已接入 —— 由 `plugins/innerCourt.js` 现算，上限 +200%（`TUNING.bonus`） |

> **契合度是门票，不是收益引擎。** 桂冈从开局到元婴，契合度只把速度从 `0.80×` 拉到 `1.04×`。真正驱动挂机收益的是 spiritRate、子嗣和行功带宽。配平时别指望靠契合度拉收益。

**实测开局数值**：同参 24.5% / 灵地 100.0% / 功法 20.0% → **综合 50.25%**，灵力/秒 **1.20**。

## 成熟度节奏

节奏旋钮只有一个：**1 现实秒 = 1 游戏小时**（`plugins/gameClock.js` 的 `SECONDS_PER_GAME_HOUR`）。

| 项 | 累积速度 | 上限 | 满值耗时 |
|---|---|---|---|
| 功法熟练度 | 每 100 游戏小时 +1% | 20% | 约 33 现实分钟 |

> **旧实现这里快了 100 倍** —— 旧公式是 `hours × 0.01` 且 `secondsPerGameHour = 2`，等于每 2 现实秒涨 1%，40 秒就顶满 20%。已修正为 `gameHours / 100 × 0.01`。
> **同参「祭炼」已整体取消** —— 同参不能升级、只能更换，切换无代价。
> 熟练度存**原始秒数**而不是百分点 —— 调参立即生效，不需要迁移存档。

## 功法分品阶

**层数不再影响契合度**（旧版的「等级 × 2%」那一项已删除）。层数现在只由修炼时长派生、在 UI 展示，不加任何属性。

| 品阶 | 层数上限 | 契合度上限（品阶分 + 覆盖率×40% + 熟练度） |
|---|---|---|
| 练气篇 | 10 | 不匹配 40% / 部分匹配 60% / 完全匹配 **80%** |
| 筑基级 | 15 | 不匹配 50% / 部分匹配 70% / 完全匹配 **90%** |
| 金丹级 | 20 | 不匹配 60% / 部分匹配 80% / 完全匹配 **100%** ✓ |

## 外功（炼体）

- **不设契合度门槛** —— 纯水磨。设计意图：内功被门槛卡住时，炼体是一条始终可推进的路
- 打坐可切换「修内功 / 修外功」，共用同一套灵力消耗
- 炼体提供**生命 / 防御**加成，随外功境界增长（1 级 生命+21/防御+2 → 18 级 生命+720/防御+72）
- 加成走**派生值**（`totalHealth` / `totalDefense`）而**不写进本体属性** —— 现有装备/灵宠加成都是双向增量加减、已有漂移风险，派生值没有任何写操作，物理上不可能漂移

## 散功重修（最小可行版）

**代价**：清空灵力与内功修为、境界回到练气一层、功法熟练度减半
**收益**：每次重修永久获得 —— 修炼速度 ×(1+次数)、灵力获取 +(10%×次数)
**外功不受影响**

# 七、对原始设计文档的修正（重要）

## 第一轮（2026-10-14）—— 已被第二轮覆盖，留档

当时发现原始设计文档有**三处数值/公式错误**：

### ① 「本命契合」公式量纲不成立
原文 `本命契合 = 境界系数 × 本命技解锁数 × 本命物收集数` —— 乘法不成立：解锁数是**计数**，没有本命技时整维归零；练气期两技两物会得到 `0.5 × 2 × 2 = 2.0`（200%）；文档自己的示例（练气 55%）也凑不出来。
当时改为加性 `境界系数 + 本命技数×10% + 本命物数×5% (+ 共鸣 15%)`。
**第二轮的处理更彻底：这一维整个删了** —— 加性写法虽然量纲对了，但它随境界自动上涨（练气 75% → 筑基自动满值），白送 26.25 个点，玩家经营不了。

### ② 结丹门槛（100%）按原文数值永远达不到
按原文推演四维上限：功法 80% / 同参 100% / 灵地 100% / 本命 100% → `综合上限 = (0.8+1+1+1)/4 = 95%`，卡死在 95%。
当时的修法是给功法分品阶、层数上限随品阶放开。
**第二轮已作废**：门槛表整体下调（结丹 85%），且功法等级不再进契合度。

### ③ 熟练度节奏不可玩
「每 100 小时 +1%」在 1 tick = 1 秒的游戏里等于 100 现实小时涨 1%。当时按 `secondsPerGameHour = 2` 重新标定。
**第二轮已重做**：常数改为 **1 现实秒 = 1 游戏小时**，熟练度满 20% 约 33 现实分钟。

## 第二轮（2026-10-15）—— 按《灵气系统》整体重做

**这不是修数值，是换体系。** 旧的五行相生相克 → 覆盖率；等权四维 → **三维加权**；灵地等级系数 → 基础产出；同参祭炼 → 取消。
数值有机器可读的断言：`npm run verify`（**234 条**：契合度 + 模块二，`scripts/verify-harmony.mjs`）。

| 项 | 旧 | 新 |
|---|---|---|
| 综合契合度 | 四维等权平均（÷4） | **三维**加权 0.15 / 0.50 / 0.35（本命维删除） |
| 本命契合 | 权重 0.35 的一维（随境界自动满值） | **整维删除** —— 改由「决定灵根」+「本命品阶封顶同参」起作用 |
| 本命品阶 | 无此概念 | 新增，封顶同参契合：`min(同参品阶, 本命品阶)` |
| 功法契合 | 五行基础分 + 等级×2% + 熟练度 | 品阶分 + 覆盖率 × 40% + 熟练度 |
| 同参契合 | 五行基础分 + 等级×3% + 祭炼 | 接近度（正主/同系列/同类型/无关）× **min(同参品阶, 本命品阶)** |
| 灵地契合 | 灵地等级系数 × (1 + 五行匹配) | 纯匹配百分比（等级改走「基础产出」） |
| 修炼速度 | `0.5 + 契合度 × 1.5` | `灵地基础产出 × (0.7 + 契合度 × 0.6) × spiritRate × 本命数量系数 × 带宽 × (1+子嗣)` |
| 门槛 | 20 / 50 / 75 / 80 / 100% | 55 / 60 / **68** / **71** / 85%，且筑基起要求灵地品阶 |
| 灵气类型 | 五行 | 五行 + **兽** + **器**（7 类） |
| 桂冈本命 | 火 + 土 | **兽 + 器**（都是**四阶**） |
| 同参祭炼 | 每 50 游戏小时 +2%，上限 20% | **取消**（同参不能升级，只可更换） |
| 功法等级 | 每层 +2% 契合度 | 由修炼时长派生，只展示，不加属性 |
| 存档 | — | `SAVE_VERSION` 2 → 3，**旧档直接清空**（数值全变） |

# 八、已知问题 / 待决策

## ✅ 已重做：功法与同参的五行选择没有区分度

**旧现象**：三本功法的契合度全是 **42.0%**，五个同参全是 **53.0%** —— 玩家选哪个都一样，五行系统形同虚设。
**旧原因**：`bestFateMatch` 对**全部本命取最大值**，而玩家两个本命互为相生，几乎任何属性都能跟其中之一凑出「相生」拿满分。

**第二轮已解决**：`bestFateMatch` 整个删除，改用**覆盖率**（功法）与**接近度**（同参）。现在开局三本功法对桂冈全是 0% 覆盖率（火/土/金 vs 兽/器），兽吼功 50%、兽器双修经 100% —— 区分度明确。

## 🔴 主线止于练气五层（**预期行为，不是 bug**）

新玩家能突破到**练气五层**，卡在「到练气六层」那道 60% 门槛上。

| 门槛 | 能不能过 | 怎么过 |
|---|---|---|
| 练气三层 55% | ✅ | 换到**元氏修命经**（金丹级，品阶分 20%→40%）→ 综合 53.25%；再把熟练度养到 **12%**（1200 游戏小时 ≈ 20 现实分钟）→ **55.05%** 过线 |
| 练气六层 60% | ❌ | 需要**三阶同参**（现有一阶，且无获取途径）或一本兽/器功法 —— 两者本批都没有 |

三层那条路径**不依赖任何未实现的获取途径**，所以第一道门槛是通的（这也正是它的设计意图：引导玩家去点切换器）。
六层断在物品获取上：兽/器功法 5 本、三阶/四阶同参、第二件本命物全部只存在于数据里，属模块四/五。

**这是有意保留的** —— 本次只落公式层，不补物品。代码里留了注释，**别当成 bug 去「修」**。

## ✅ 已解决：本命维开局即饱和
旧的四维版里「本命契合」开局就是 75%（白送综合 26.25 个点），且筑基时境界系数一带就把整维顶满，权重最高却毫无成长空间。**第二轮已整维删除**，本命改为通过「决定灵根」和「本命品阶封顶同参契合」起作用。

## 🟡 没有离线收益
`initializePlayer()` 里没有任何时间差补偿，关掉页面进度就停住，回游戏不会补算。对应原始设计文档的**模块九·离线结算**，尚未实现。

> 时钟本身已经建好了（`plugins/gameClock.js`，含 `MAX_TICK_REAL_SECONDS = 5` 的钳制 —— 防止后台标签页被节流后切回来一次性灌进几小时收益）。接离线结算时复用它的边界钩子即可，但 `persistence` 里还**没有** `lastOnlineRealTime` 字段。

## 🟡 每秒整包存档
`gainSpirit` 每秒被调用一次，结尾都 `saveData()` —— 每秒把整个 state 加密写一次 IndexedDB，比较重。上游有过一个「修复内存溢出问题」的提交。可考虑加节流。

## 🟡 成就系统里有三个字段名对不上
`achievements.js` 引用了三个 store 上**不存在**的字段，导致「装备 / 秘境连杀 / 高阶炼丹」三类成就永远无法达成（有可选链兜底，不会报错，属静默失效）：
- `player.equipment` → 应为 `Object.values(equippedArtifacts)`（注意它是对象不是数组）
- `player.dungeonStreakKills`、`player.highQualityPillsCrafted` → 无对应字段

未修，因为成就要被新模块替换。

2. **headless 浏览器冒烟** —— 本机**有** Chrome：`C:\Program Files\Google\Chrome\Application\chrome.exe`
   ```bash
   npx vite --port 2025 &
   "/c/Program Files/Google/Chrome/Application/chrome.exe" --headless=new --disable-gpu \
     --user-data-dir=/tmp/chrome-smoke --enable-logging=stderr --v=1 \
     --virtual-time-budget=15000 --dump-dom "http://localhost:2025/#/cultivation"
   ```
   `--enable-logging=stderr --v=1` 会把页面的 `console` 原样打出来（grep `INFO:CONSOLE`）。2026-10-15 那次返工就是靠它抓到 `factory is not a function` —— `modules/index.js` 对没有 `state` 导出的模块兜底成 `{}`，把整个 store 装配搞崩了。
