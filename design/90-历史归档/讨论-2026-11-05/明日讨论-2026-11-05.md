## A 类：不定就没法开工

### A1. 子嗣功法加成走哪个乘区

**现状**

- 子嗣有两条数值线：
  - **修炼** —— `offspringCultivationGainOf`（`plugins/innerCourt.js:2039`），日增 = 基础 × 灵根系数 ×
    (1+同参) × (1+灵地 +4%) × (1+词条)，词条那一项按境界套软上限（qi 2.0）。
  - **战力** —— `secretRealm.buildOffspringUnit`（`plugins/secretRealm.js:390`），
    `realm × root × fate × (1+词条) × base + 装备面板`。
- 模块一硬口径：**非心法效果只有桂冈吃**（`artEffects.js` 顶部注释），子嗣吃不到。
  藏书阁等于要给子嗣开一条**新通道**，开在哪条线上是本次最大的分叉。
- 子嗣目前没有任何「功法」字段。

**要定的分叉**

1. 加成只加**修炼速度**、只加**战力**、还是**按类别分两路**（心法 → 修炼 / 法术·身法·炼体·器诀 → 战力）？

**建议**

- **只加修炼速度（MVP）**：`日增 × (1 + b)`，`b = 0.05 × artCoverage × artEffectCoefOf(art)`。
- 理由：① 不改「非心法效果子嗣吃不到」这条硬口径；② 不碰 `sim:realm` 的秘境阈值校准；
  ③ 藏书阁挂在封地/养成线上，玩家要的就是子嗣练得快（修炼位只覆盖 8%~20% 的人，速度是真瓶颈）。
- **上限写死 ≤20%**。⚠ 按 `sim:offspring` 的基线，加成 ≥18.5% 就能把**五灵根 142 岁筑基**
  压到 120 岁以内，直接推翻「五灵根死也筑基不了」这条硬口径 —— 这个上限是保护线，不是随手取的。
- 分两路（方案 B）留作第二批：它要改 CLAUDE.md 的一条硬口径 + 重算秘境难度，不值得和第一版一起做。

**影响**：`sim:offspring` 增加一档 `--art=`（默认 0）重跑并同步校准表；断言 **4~6 条**
（池子过滤 / 权重 / 20% 上限 / 无灵根 = 0）；产出登记无需新增（子嗣修炼不是货币产出）。

**出处**：《模块四》§十三 · 《模块一》§15.2 / §9.1 · 《功法系统》§四 · `innerCourt.js:2039` / `:355`。

### A2. 灵根 ↔ 功法的匹配表

**现状**

- 子嗣的灵根 = 本命 `fateElement` 去重集合，元素共 7 种：
  `metal / wood / water / fire / earth / beast / vessel`（`items.js` 的 `FATE_ELEMENTS`），
  子嗣身上落在 `child.roots` 数组，1~5 个。
- 功法自带 `elements` 数组，取值同上，另有 `['universal']`（通用）和 `[]`（无属性）。
- 现成函数 `harmony.artCoverage(art, elements)`：`universal` → 1；`[]` → 0；
  其余 = `交集大小 / 修士元素数`。

**要定的分叉**

1. 匹配用 `artCoverage > 0` 就行，还是另建一张「灵根 → 可学功法类别」的表？

**建议**

- **直接用 `artCoverage > 0`**，不新建表。理由：它已经是全仓库唯一的「功法 × 修士属性」判定，
  语义就是「这门功法的灵气被这名修士覆盖了多少」；>0 = 有交集 = 能学。
- 三条细则一起定掉：`universal` 对所有人匹配；`elements: []` 的功法**对所有人都不匹配**
  （与《功法系统》§8.2 #9「暂按 0」一致）；**无灵根子嗣永不匹配**（凡人学不了功法）。
- **已知预期行为（不是 bug）**：桂冈开局只有 3 本（火 / 土 / 金），木 / 水 / 兽 / 器灵根的子嗣
  一开始抽不到，要等桂冈学了新功法才缓解。原备忘录自己就写了这条。

**影响**：0 新增函数、0 新增表；断言 2 条（universal / 空元素）。

**出处**：《模块四》§十三 · 《功法系统》§2.1 / §8.2 #9 · `harmony.js:204` · `items.js:36`。

### A3. 子嗣功法吃不吃品阶

**现状**

- 功法 90 本走**四阶四品十六档**编码（`qi_low` … `nascent_peak`），品阶分只在桂冈的门槛里用。
- `artEffectCoefOf(art) = 1.12^score`，`score = 3×(阶−1) + 品序(low 0 / mid 1 / high 2 / peak 3)`，
  一阶下品 → 四阶极品 = **1.000 ~ 3.896**。

**要定的分叉**

1. 抽到哪本都一样给固定加成，还是按品阶缩放？

**建议**

- **吃品阶**，直接乘 `artEffectCoefOf`。理由：设计写的是「抽到弱的接受」——
  有强弱才有「抽」的意义；复用现成系数，零新增表。
- 实际池子上限由**桂冈已学**决定：练气期多为 T1/T2 功法 ⇒ 系数落在 **1.0~2.21**，
  配合 A1 的 5% 底数就是 **5%~11%**，正好压在 20% 保护线以内。金丹期桂冈学了 T3 才可能摸到十几。

**影响**：与 A1 同一条断言覆盖。

**出处**：《功法系统》§1.2 · 《真值表》§5.10b · `cultivationData.js:22` · `artEffects.js:71`。

### A4. 藏书阁 Lv1~3 干什么

**现状**

- `estate.js` 里藏书阁 `maxLevel: 3`、`tier: 'large'`、乡侯府 Lv5 解锁、`produces: null`。
- 《模块四》§十三 只写了系统行为，**没写等级的作用**。代码必须落一个行为，否则 2/3 级是纯装饰。

**要定的分叉**

1. 等级不加成（Lv1 即全功能，2/3 级只算建筑完成度）？
2. 等级加成强度？
3. 等级影响功法池（例如解锁更高品阶）？

**建议**

- **加成强度实时相乘**：`× (1 + 0.15 × (等级 − 1))` —— Lv1 **1.0** / Lv2 **1.15** / Lv3 **1.30**。
- **实时读当前建筑等级、不存快照**：升级立即生效，不用重抽，老档零迁移。
- A1 的 **20% 上限放在等级乘区之后再夹一次**，所以 Lv3 也不会突破保护线。
- 不选「等级解锁更高品阶」：池子已经受「桂冈已学」限制，再加一层闸门会变成双重锁，玩家看不懂。

**影响**：1 条断言（Lv1/2/3 倍率与上限夹取）。

**出处**：《模块四》§十三 / §十六.1 · `estate.js:267`。

### A5. 触发时机的边界（三处必须写死）

**现状**

规则原文：**落成时一次** + **之后每个子嗣到筑基时再触发一次**；只学 1 门、不可替换。
但下面三件事没写：

**要定的分叉**

1. **落成时给谁抽？** 建议：**当时在世、有灵根、还没学过的全体子嗣**（含已经筑基 / 金丹的）。
2. **落成后才出生的子嗣什么时候抽？** 建议：**出生时不抽，到筑基那天抽**（规则第二句就是为这批人写的）。
3. **已经学过的人到筑基还抽吗？** 建议：**不抽**（不可替换）；**当时没匹配到的到筑基再试一次**
   （这时桂冈可能学了新功法，池子变大了）—— 这才是「再触发一次」的实际意义。

**建议**：三条按上面写死，全部走**幂等**（同一子嗣同一次触发不会重复抽），
触发点放在 `advanceInnerCourtDay` 的修炼结算之后、与 `realmLevel` 升级同一处。

**影响**：断言 3 条（幂等 / 无灵根 = 0 / 已学不重抽）。

**出处**：《模块四》§十三 · `stores/modules/innerCourt.js` 的 `advanceOffspringCultivation`。

## B 类：开工前一周定

### B1. 离线时间重审（筑基 + 金丹）

**现状**

- 现在**三段都按 180 游戏天**：练气 = 4.8 现实小时、筑基 = **12 现实分钟**、金丹 = **1.7 现实分钟**。
- 结算性能实测约 **0.037 秒 / 游戏天**（180 天 7.9 秒、3,650 天 136 秒）。
- 180 天是性能权宜，**不是设计标准**（《下一步》新待办 · 2026-11-03 #1）。

**要定的分叉**

1. 配额按**现实时长对齐**（各段都 ≈ 4.8 小时）？筑基要 4,320 天（≈160 秒结算）、
   金丹要 30,240 天（≈1,119 秒结算）—— 翻页就卡死，**否决**。
2. 配额按**可接受的结算时长**定？
3. 先做**跨期聚合结算引擎**再把配额放开？

**建议**

- 走 **2**：以「结算 ≤60 秒」为性能预算 ⇒ 两段都定 **1,500 游戏天**
  （筑基 **1.7 现实小时**、金丹 **14 现实分钟**），离线报告里写明本段折算。
- 聚合引擎单独立项（《下一步》R34 性能债），做完再把配额抬到与练气一致。
- 代价说清楚：金丹期「挂一晚」只能收 14 分钟的量，这是**已知缺口**，不是 bug。

**影响**：`plugins/offline.js` 的配额表 + 3 条 `verify-offline`；不改产出登记（只改时间窗）。

**出处**：《下一步》新待办 2026-11-03 #1 · 《模块九》§一 · 《真值表》§0.1。

### B2. 挂账 / 秘库时钟错配

**现状**

- 俸禄按**游戏时间**发（练气按月、筑基后每游戏年），秘库按**现实时间**刷（48 现实分钟/月）。
- 金丹段：每游戏年 = 365 × 0.571 秒 ≈ **3.5 现实分钟**发 2,500 二阶挂账；
  秘库 48 分钟才刷一次、货架容量约 2,700~3,000 点 ⇒ **约 40 倍缺口**。筑基也约 **6.5 倍**。

**要定的分叉**

1. 俸禄也改挂 `faction.realSeconds`（与飞鹰门同一时钟）？
2. 秘库 / 老九改跟游戏月？
3. 补一个挂账出口（大库 / 洞府租赁）？

**建议**

- **① + ③**：俸禄改挂现实秒 —— 筑基变成 24.3 现实分钟/期，对上 48 分钟/刷，**约 0.5 倍、配平**；
  金丹仍约 40 倍，靠 **③ 大库**（排在 B8-b）当出口。
- **② 否决**：秘库跟游戏月后，金丹段 17 秒刷一次货架，等于自动刷货机。
- ⚠ 不要用「抬价」去盖缺口（《下一步》已写死）。

**影响**：`plugins/salary.js` 一处时钟源 + 3 条断言；大库页面归 B8-b，本批不动 UI。

**出处**：《下一步》新待办 2026-11-03 #2 · 模块五 §13.3 · CLAUDE.md「门派俸禄」条。
