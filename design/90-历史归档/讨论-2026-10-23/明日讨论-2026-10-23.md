## 1. 🔴 重点课题 A：「所有装备给属性」—— 先定属性从哪来

> **一句话结论**：现在的状态不是「所有装备都没属性」，而是
> **「所有属性都来自 13 个部位模板，其中 9 个部位根本没有物品能穿」**。
> 所以这句话至少要拆成「范围 / 粒度 / 来源 / 平衡」四个问题，不能直接开工。

### 1.1 这句话可能指四件事（先选范围）

| # | 解释 | 现状 | 工作量 |
|---:|---|---|---|
| A | **每件装备都有面板**（现在有例外：开局五件、本命物没有） | 灵器实例都有 `stats`（`createItemInstance` 生成）；开局五件只有同参身份 | 小 |
| B | **每个部位都能穿到东西**（现在 9/13 个部位没有物品池来源） | 物品池只能填 weapon / body / ring1 / artifact；head 只能靠 3 条炼器配方；其余 8 个槽完全无来源 | 中（补物品或删槽） |
| C | **每件装备给全部四维 / 独立属性**（现在同部位所有装备面板一样） | 104 件灵器只有 4 套实际生效的白板；`artifact` 43 件的一阶白板全是攻 6 / 防 4 | 中大（要补底材数据） |
| D | **装备也带高级词条**（暴击/连击/闪避/吸血…） | 词汇表有 19 条，但只有洗练能加，且洗练对灵器会崩（P34） | 大（依赖 P34） |

> **建议先答**：A + B + C 是「所有装备给属性」的正解；D 放到装备词条体系里单独谈。
> 只做 A 等于没改（灵器本来就有面板），只做 B 等于补掉落、不解决「同部位全一样」。

### 1.2 现状证据（文档 vs 代码）

#### (1) 灵器是「部位白板」，不是「每件装备的属性」

`src/plugins/equipment.js:83` 的 `SLOT_BASE_STATS` 只有 13 个部位模板：

| 部位 | 一阶白板 | 部位 | 一阶白板 |
|---|---|---|---|
| 武器 | 攻 10 | 项链 | 生命 60 |
| 头部 | 防 6 / 生命 40 | 戒指1 / 2 | 攻 8 |
| 衣服 | 防 8 / 生命 60 | 腰带 | 防 4 / 生命 40 |
| 裤子 | 防 5 / 生命 30 | 手套 | 攻 6 |
| 鞋子 | 防 4 / 速 2 | 护腕 | 防 4 |
| 肩甲 | 防 6 / 生命 40 | 法宝 | 攻 6 / 防 4 |

`generateEquipmentStats(slot, tier, quality)` 只看部位、基阶、成色（`equipment.js:114`）。
所以 104 件灵器 → 只有 4 套实际生效的面板；「寒冰刺」和「青玉寒水剑」如果是同部位同阶同成色，
面板**一模一样**。

⚠ **设计文档原本不是这么写的**：
- 《模块一》§9.2 的物品结构里写的是底材自带 `equipmentStats`（灵器/灵岩有）；
- 《[物品池设计方案](../../30-数据与决议/物品池设计方案.md)》§4.2 写的是
  `stats: generateEquipmentStats(type, tier, quality)` —— **按 type，不是按 slot**。
- 代码实现成了按 13 部位，和这两处都对不上。

#### (2) 13 个部位里，物品池只能填 4 个

`EQUIP_SLOT_BY_ITEM_TYPE`（`equipment.js:43`）把中文 type 映射到 13 个槽位。
按当前 570 件池子的实际 type 统计：

| 槽位 | 池内可穿件数 | 来源 |
|---|---:|---|
| 武器 | **54** | 飞剑 20 / 刺 9 / 刀 5 / 矛 4 / 棍 4 / 匕 2 / 锤 2 / 杖 1 / 鞭 1 / 弩 1 / 枪 1 / 戈 1 / 镖 1 / 弓 1 / 轮 1 |
| 衣服 | **6** | 袍 |
| 戒指1 | **1** | 戒 |
| 法宝（兜底） | **43** | 盾 3 / 牌 9 / 袋 4 / 幡 3 / 器 3 / 环 3 / 伞 2 / 梭 2 / 盘 2 / 印 2 / 塔 1 / 镜 1 / 铃 1 / 钹 1 / 简 1 / 砚 1 / 网 1 / 索 1 / 舟 1 / 丹炉 1 |
| 头部 | **0**（只能炼器） | 金簪 / 金钗两条 `head` 配方（另有素金戒指 `ring1`） |
| 裤子 / 鞋子 / 肩甲 / 手套 / 护腕 / 项链 / 戒指2 / 腰带 | **0** | 池子里没有 `裤/履/靴/肩甲/手套/护腕/珠/项链/腰带` 这些 type |

→ 物品池只能填 **4 个槽**；头部只能靠 3 条炼器配方；剩下 **8 个槽**
（裤 / 鞋 / 肩甲 / 手套 / 护腕 / 项链 / 戒指2 / 腰带）**完全没有来源**。
`equippedArtifacts` 里那 13 个槽的 `null`（`src/stores/modules/attributes.js:43`）不是「还没打到」——
其中 **8 个是物品池里根本没有对应 type**。

#### (3) 43 件「法宝」全吃同一套攻 6 / 防 4

盾、牌、幡、袋、塔、伞、镜、印、钹……全部落到 `artifact`。
所以「饕餮纹白玉牌」的一阶白板是攻 6 / 防 4，「灵藤木盾」也是攻 6 / 防 4 ——
**盾不加防御、牌不给气血**。这是「所有装备给属性」最直观的反例。

#### (4) 开局五件只有同参身份，没有装备面板

`taotie_shield`（盾）、`qingyu_sword`（飞剑）、`jinggang_ci`（刺）、`lingteng_shield`（盾）
在代码里是 `FATE_ITEMS` 的兼容视图（`cultivationData.js:166`），
**不是背包里的装备实例**，没有 `stats`，也不能穿。
小说里它们明明是装备；《下一步》P11 就记过这个「同一批物件被两套系统各记一半」的问题。

#### (5) 高级属性有词汇表，但没有来源

`attributes.js` 定义了 6 条战斗属性 + 6 条抗性 + 7 条特殊属性；
`equipment.js:143` 的 `reforgeableStats` 每个部位只列 3 条候选，且只有洗练能加。
洗练现在对灵器会抛 `TypeError`（P34），所以这 19 条属性**实际上全部为 0**。

#### (6) 子嗣战力公式里没有装备项

《数值真值表》§5.5 的子嗣战力：

```
四属性 = 基础值（生命 60 / 攻击 6 / 防御 3 / 速度 8）
       × 境界系数 × 灵根系数 × 本命系数 × (1 + Σ词条)
```

**没有装备乘区**。而《模块二》§15.3 又规定子嗣有 4 个装备槽（攻/防/同参/灵兽）。
如果「所有装备给属性」包括子嗣，就要先定装备怎么进这条公式（加算 / 乘算 / 只做战力展示）。

#### (7) 炼器产物与宝匣灵器是两套形状，数值锚点还对不上

- 炼器产物：`type = slot`（英文）、`quality = 'common'`、`stats` 来自配方；
- 宝匣灵器：`type` 是中文形态、`equipSlot` 是部位、成色是中文；
- `equipment.js:80` 注释说「一阶白板锚点取炼器三条配方（金簪防 6 + 生命 60）」，
  但 `SLOT_BASE_STATS.head` 实际是**生命 40**，配方金簪是**生命 60** —— 两边不一致。
- P32 的回收口也明确排除了炼器产物（没有 `category/tier`，成色是英文键），
  见《[当前实现](../../00-总览与状态/当前实现.md)》§四「炼器产物不在回收口」。

### 1.3 需要定（Q A1~A7）

#### A1. 「所有装备」的范围

四选一或组合：**A 每件都有面板 / B 每个槽都有货 / C 每件独立属性 / D 高级词条**。
建议 **A+B+C 一次做，D 另开**。

#### A2. 属性来源：部位白板，还是底材自带？

- 方案 1：继续按部位（现状），只补「每件底材 ±20% 浮动」；
- 方案 2：底材自带 1~2 条主属性（如飞剑必攻、盾必防/血），部位只做兜底；
- 方案 3：底材主属性 + 部位副属性（两段相加）。

建议 **方案 2**：104 件灵器各给 1~2 条主属性，工作量可控，也解决「同部位全一样」。
《模块一》§9.2 和《物品池设计方案》§4.2 本来就是按 type 写的，方向一致。

#### A3. 13 个槽位怎么处理

- 方案 1：补齐 8 个空槽的物品 type（裤/鞋/肩甲/手套/护腕/项链/戒指2/腰带），
  每个至少 3~5 件；
- 方案 2：**砍槽**——主角也只保留 8~10 个槽，删掉池子里永远填不上的；
- 方案 3：把 8 个空槽改成「同一槽多形态」（如 `ring1/ring2` 合并成「戒指」，可戴 2 只）。

建议 **方案 1 的缩小版**：先补「项链 / 腰带 / 护腕 / 鞋」4 个有明确小说意象的槽，
其余 4 个（肩甲 / 裤子 / 手套 / 戒指2）暂时保留 UI 但标「暂无产出」，别为了填槽硬造物品。

#### A4. 高级属性从哪来

- 固定词条（每件装备天生 1 条，如飞剑 +暴击）；
- 随机词条（掉落时 roll，成色决定条数）；
- 只靠洗练（现状，但洗练已坏）。

建议 **固定 1 条主词条 + 洗练改数值**，不要做「掉落随机词条」——
会和子嗣的「词条 5/10/20%」撞名，也会让背包里全是不可比的装备。

#### A5. 子嗣装备怎么进战力公式

- 方案 1：装备属性直接加到四属性上（加算），再乘境界/灵根/本命；
- 方案 2：装备单独一个乘区（乘算），和本命并列；
- 方案 3：只影响「战力」展示，不影响实际战斗。

建议 **方案 1**：加算最直观，也和桂冈的 `baseAttributes + 装备` 管线一致；
代价是要重算子嗣的成长曲线（见 A7）。

#### A6. 平衡与登记：要不要重跑怪物阈值

《下一步》P25 的校准队伍是 **3 名同境界单灵根子嗣、无装备**；
「所有装备给属性」会整体抬高战力，现有怪物阈值（`realmCoefAt(E) × 4.5`）会变松。

- 要不要重跑 `npm run sim:realm` 重算阈值？
- 装备属性只影响战斗，按 P29 口径**不进修炼/门槛**，但要不要登记《产出登记表》？

建议：数据落地后**重跑一次 `sim:realm`**，把「有装备的校准队伍」作为新基准；
装备属性登记到《数值真值表》新小节（§5.9），产出侧只登记「装备战力」这一条，不重算修炼门槛。

#### A7. 要不要顺手解决「桂冈攻击永远 10」

《下一步》P25 末尾的待议：桂冈境界不加战斗属性，炼体满 18 级也只有攻 10；
练气二层单灵根子嗣攻击已经 17。**装备给得再多，桂冈仍然是个肉盾。**

三个方向（原文）：
1. 桂冈也套境界系数（最彻底，动镇守平衡）；
2. 只给攻/血/防加一条随内功境界的成长（如每层 ×1.12，改动小）；
3. 不改，定位纯肉盾。

建议 **方向 2**，和本课题一起拍；否则「所有装备给属性」只惠及子嗣，桂冈还是上不了场。

### 1.4 建议汇总（可改）

1. **范围**：A+B+C；D 另开。
2. **属性来源**：底材自带 1~2 条主属性 + 部位兜底（方案 2）。
3. **槽位**：先补 4 个有小说意象的槽，其余标「暂无产出」，不硬造。
4. **高级属性**：固定 1 条主词条，洗练只改数值。
5. **子嗣**：装备加算进四属性，再乘境界/灵根/本命。
6. **平衡**：落地后重跑 `sim:realm`；装备面板登记《数值真值表》§5.9。
7. **桂冈**：同轮拍「每层 ×1.12」的方向 2。

## 2. 🔴 重点课题 B：「同参适合度」细化 —— 先分清两条轴

> **一句话结论**：现在不是「档位不够」，而是
> **「0.25 是个大口袋（91/104 件灵器都在这一档），而且完全同型的反而拿 0.25、只是同组的拿 0.4」**。
> 所以先修判定倒挂，再谈要不要加档；否则加再多档也是建在错的判定上。

### 2.1 现状：设计六档 vs 代码判定

**设计表**（《模块一》§4.3 / 《物品池设计方案》§6.1）：

| 档 | 系数 | 设计判定 |
|---|---:|---|
| 正主 | 1.0 | `name` 完全相同 |
| 准正主 | 0.8 | 同 category + 同 series + 名字近似 |
| 同系列 | 0.6 | 同 category + 同 series |
| 近类型 | 0.4 | 同 category + 同 kind（**开局五件硬编**） |
| 同类型 | 0.25 | 同 category（判定规则待定） |
| 无关 | 0.1 | 其余 |

**代码**（`src/plugins/items.js:133` 的 `affinityOf`）：

```js
if (item.name === master.name) return { tier:'owner', coef:1.0 }
if (sameSeries && isNearName(...)) return { tier:'quasiOwner', coef:0.8 }
if (sameSeries) return { tier:'series', coef:0.6 }
if (sameCategory && isNearKind(...)) return { tier:'nearType', coef:0.4 }
if (sameCategory) return { tier:'type', coef:0.25 }
return { tier:'none', coef:0.1 }
```

其中 `isNearKind`（`items.js:119`）**在 typeA === typeB 时直接返回 false**：

```js
if (!typeA || !typeB || typeA === typeB) return false
return (TYPE_GROUPS[category] || []).some(g => g.includes(typeA) && g.includes(typeB))
```

→ **完全同型 → 不走 `nearType` → 落到 0.25；只是同组 → 0.4。判定倒挂。**

### 2.2 实测分布（570 件池子，对两个本命）

| 本命 | 正主 1.0 | 准正主 0.8 | 同系列 0.6 | 近类型 0.4 | 同类型 0.25 | 无关 0.1 |
|---|---:|---:|---:|---:|---:|---:|
| 刃背乌鬣猪（灵兽/妖兽） | 1 | 2 | 3 | **68** | **16** | 480 |
| 饕餮纹暗金镶青金石玉牌（灵器/牌） | 1 | 0 | 3 | **9** | **91** | 466 |

两处倒挂可以直接看出来：

- 灵兽：**16 件「妖兽」**（和本命完全同型）拿 0.25；68 件其它灵兽（灵兽/凶兽/异种）拿 0.4；
- 灵器：**6 件「牌」**（和本命完全同型）拿 0.25；9 件「戒 / 环 / 铃 / 镜 / 印 / 钹」拿 0.4。

0.25 这档里都有什么（灵器/牌本命）：

| type | 件数 | type | 件数 |
|---|---:|---|---:|
| 飞剑 | 20 | 袋 | 4 |
| 刺 | 9 | 棍 | 4 |
| 袍 | 6 | 器 | 3 |
| 牌 | 6 | 幡 | 3 |
| 刀 | 5 | 其余 20 种 | 31 |
| 矛 | 4 | | |

→ 一把飞剑、一件道袍、一面幡、一个丹炉，对「玉牌」本命**全是 0.25**。
这不是「颗粒度不够」，是**0.25 这档没有区分度**。

### 2.3 五个具体缺口

1. **判定倒挂**：完全同型 0.25 < 同组 0.4（§2.2）。
2. **0.25 是口袋**：91/104 件灵器同档，跨形态（剑 vs 袍 vs 幡）没有差别。
3. **形态分组太粗**：`TYPE_GROUPS`（`items.js:104`）里
   - `['盾','袍','冠','服饰']` 一组 → 盾和道袍算「近类型」；
   - 15 种近战武器一组 → 飞剑和狼牙棒算「近类型」；
   - 灵材四组（金属/宝晶、灵土/灵木、骨材、花/果/叶）也算近类型。
4. **跨 category 一刀切 0.1**：灵植「草」和灵材「叶/花」是同一株植物的不同部位，
   现在算「无关」；灵兽和骨材同理。
5. **子嗣侧根本没有颗粒**：子嗣的同参契合是写死的 `companionFit: 0.6`
   （`src/plugins/innerCourt.js:333`），所有子嗣、所有本命、所有物品都 0.6。
   如果「细化颗粒」包括子嗣，这一条比桂冈的六档更粗。

另外两条已知的「先硬编」遗留：

- **开局五件**不走动态判定（`harmony.js:291` 先读硬编 `affinity`）：
  盾对本命玉牌是同系列（taotie），按规则应是 0.6，硬编为 0.4 —— 为了保住
  「开局 0.08 → 吕氏 0.152」的破境数学；
- **准正主**的 `isNearName` 是占位实现（一个名字包含另一个，`items.js:95`），
  没有正式规则。

### 2.4 需要定（Q B1~B7）

#### B1. 颗粒度指哪条轴？

- **判定轴**：同一件物品对同一本命的档位（六档 → 更细）；
- **对象轴**：同参只算桂冈，还是每个子嗣各算各的（现在子嗣固定 0.6）。

建议 **先答对象轴**：如果子嗣不做，判定轴只影响桂冈一个人的修炼速度；
如果子嗣要做，就得先定「子嗣的本命从哪来 / 同参槽怎么选 / 老档怎么迁移」，
工作量差一个量级。

#### B2. 判定倒挂怎么修？

- 方案 1：`isNearKind` 允许 `typeA === typeB` → 完全同型也走 0.4；
- 方案 2：新增「同型」档 0.5，排在「近型 0.4」之上；
- 方案 3：把「同类型 0.25」改名为「同类」，明确它只表示同 category。

建议 **方案 1 + 3**：先修倒挂、把 0.25 改名，不新增系数；
如果网页端愿意重算，再加方案 2 的 0.5。

#### B3. 0.25 这档要不要再拆？

- 方案 1：保持 0.25，接受「同 category 其它形态」都是 0.25；
- 方案 2：按形态距离拆成 0.3 / 0.25 / 0.2（如「武器↔防具」0.2，「武器↔武器」0.3）；
- 方案 3：做「标签相似度」连续分（series / type / 形态 / 材质 / 用途加权），
  再映射回六档 —— 这是《模块一》§十一写的目标方案。

建议 **v1 先做 B4 重分组 + B2 修倒挂**（零新增系数、不用重算）；
如果网页端愿意重算，再做 **方案 2** 的 0.3 / 0.25 / 0.2 形态距离；
**方案 3** 等物品池再扩时做。

#### B4. 形态分组怎么重划？

现 `TYPE_GROUPS` 是手写的，建议按「持握 / 穿戴 / 佩挂 / 容器 / 乐器 / 法器 / 坐骑」重分：

| 组 | 灵器 type |
|---|---|
| 持握（近战） | 飞剑 / 剑 / 刺 / 匕 / 刀 / 矛 / 枪 / 戈 / 棍 / 杖 / 锤 / 鞭 / 斧 / 钩 / 叉 |
| 持握（远程） | 弓 / 弩 / 镖 |
| 穿戴（防具 / 头饰） | 袍 / 甲 / 冠 / 簪 / 履 / 靴 / 裤 / 腰带 / 护腕 / 手套 / 肩甲 |
| 持盾 | 盾 |
| 佩挂 | 戒 / 环 / 珠 / 铃 / 镜 / 牌 / 印 / 玺 |
| 容器 | 袋 / 网 / 索 / 伞 / 舟 / 塔 |
| 乐器 / 文房 | 琴 / 笛 / 笔 / 砚 / 图 / 简 |
| 法器 / 杂项 | 幡 / 旗 / 符 / 盘 / 轮 / 梭 / 丹炉 / 器 |

这同时解决「盾和道袍算近类型」的问题。

#### B5. 跨 category 要不要给档？

灵植 ↔ 灵材同源（草 ↔ 叶/花，树 ↔ 灵木/果），现在 0.1。
建议给一个「同源」档 **0.15**（低于同类 0.25，高于无关 0.1）；
但这会新增系数，必须按 B7 处理。

#### B6. 五行 / 灵气要不要进判定？

物品有 `fateElement`（7 种），本命有 `element`（兽/器），但**当前判定完全不看灵气**。
《物品池设计方案》§九已把「element 单值 → 数组」列为待办，并注明改动面广。
建议 **本轮不做**；等灵地/功法元素体系一起返工时再加。

#### B7. 改判定要不要重算门槛？

**必须区分两种情况**：

- **只改判定、不加/不改系数**（B2 方案 1、B4 重分组）：
  锚点配置（盾 0.4 / 猪妖 0.6 / 准正主 0.8）不变，
  开局 0.08 → 吕氏 0.152、六层 0.24 的破境数学不受影响；
  只是玩家可选物品的档位变化，**不需要按宪法第二章重算**。
- **新增档位 / 改系数**（B2 方案 2、B5 的 0.15）：
  必须按《最高宪法》第二章重算；而且要检查会不会让人提前跨门槛。
  粗算：0.5 的同型档 × 最高练气功法 0.4 = 0.20 < 六层 0.24；
  九层 0.6 × 0.5 = 0.30 < 0.40，**不会跳门槛**，但速度会变快。

### 2.5 建议汇总（可改）

1. **对象轴**：v1 只做桂冈；子嗣同参另开（先把 4 槽和本命来源定了）。
2. **倒挂**：先改 `isNearKind` 允许同型 → 完全同型 0.4，不改系数。
3. **0.25**：改名「同类」；v1 先不拆，等 B4 重分组后再看要不要拆 0.3 / 0.25 / 0.2（拆就要按 B7 重算）。
4. **形态**：按 B4 的 8 组重划，替换现在的 `TYPE_GROUPS`。
5. **跨类**：先记「同源 0.15」为待定，不本轮落地。
6. **五行**：不做，等元素体系返工。
7. **硬编五件**：保持不动；等「所有装备给属性」把开局五件做成真装备时，
   再决定它们的同参档位要不要跟着改。
