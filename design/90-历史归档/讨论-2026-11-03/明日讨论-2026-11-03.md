## A 类：不定就没法开工

### A1. 金丹加速：「4 现实秒 = 1 游戏周」的倍率切换与离线配额

**现状**

- **唯一时间锚点 = 96 现实秒 / 游戏天（练气期）**。筑基后 **24×**，即同一锚点被压缩，
  **不是第二个锚点**。代码：`gameClock.js` 的 `ASCENDED_TIME_SCALE = 24`，判据是布尔
  `isAscendedLevelOf`（内功 ≥ 11）。
- 当前两档的实际节奏：

  | 档 | 倍率 | 1 现实秒 | 1 游戏天 | 1 游戏年 |
  |---|---:|---|---:|---|
  | 练气 | 1× | 15 游戏分（1 整步） | 96 现实秒 | **9.73 现实小时** |
  | 筑基 | 24× | 6 游戏小时（24 整步） | **4 现实秒** | **24.3 现实分钟** |
  | 金丹（目标） | **168×**（24×7） | **42 游戏小时（168 整步）** | **0.571 现实秒** | **3.48 现实分钟** |

- 目标口径反推：**4 现实秒 = 1 游戏周** ⇒ 1 游戏天 = 4/7 ≈ **0.571 现实秒** ⇒ 相对 24× 再快 **7 倍**
  ⇒ 总倍率 **168×**。此时 **1 现实小时 = 6,300 游戏天 ≈ 17.3 游戏年**。
- **步长不变**：`GAME_STEP_SECONDS = 900`（15 游戏分）。`advance()` 每 tick 走 **168 步**，
  `checkBoundary` 按单位逐个补触发 —— 一 tick 跨 1.75 游戏天，小时触发 42 次、天触发 1~2 次，
  现有实现能扛（`gameClock.js:178` 的 `for (i = prevUnit+1; i <= nextUnit; i++)`）。
- **离线配额现在是「游戏天」**：`OFFLINE_TUNING.maxGameDays = { qi: 180, ascended: 180 }`
  （筑基设计值 3,650 等聚合引擎，R33）。换算：练气 180 天 = 4.8 现实小时；筑基 180 天 = 12 现实分钟；
  **金丹 180 天 = 103 现实秒（1.7 现实分钟）** —— 离线 1 小时只结算 1.7 分钟，等于配额失效。
- **其它按境界取倍率的消费点**：`offlineSimulation.js:31` 的 `GAME_SECONDS_PER_REAL_SECOND_ASCENDED`、
  `stores/modules/exploration.js:33` 的叙事换算（练气 900 / 筑基 21,600 游戏秒），
  两处都只认布尔，第三档要一起改。
- **三个派生周期会跟着变快 7 倍**：
  - **俸禄**：筑基后「每游戏年发一次」（`salary.js` 的 `salaryDueMonths`）→ 金丹下 **每 3.5 现实分钟**
    发一年，下柱 833 二阶 / 3.5 分钟 ≈ **14,300 二阶/现实小时**。
  - **挂账**：90% 只能买秘库，而秘库月刷 / 老九倒计时走的是 **`faction.realSeconds`（现实秒）**，
    不跟 24× 加速 → **挂账会以 7 倍速堆积，消费口不增长**。
  - **探索事件**：24× 下已是 **3 个/现实秒**（`CLAUDE.md` 硬口径），168× 下约 **21 个/现实秒**。
- **日结性能**（P55-c 实测，真实档 666 子嗣 / 12,189 物品）：180 游戏天 = **7.9 秒**，
  3,650 游戏天 = **136 秒**。折算 ≈ 44 ms/游戏天；金丹每 tick 跨 1.75 天 ≈ **77 ms/tick**，
  在 1 秒 tick 预算内；但月/年边界每 17 现实秒就来一次。

**要定的分叉**

1. **倍率怎么表达**：新增第三档 `CORE_TIME_SCALE = 168`，还是改成按段查表
   `{ qi: 1, foundation: 24, core: 168 }`？判据从布尔 `isAscendedLevelOf` 换成
   `realmTierOf()`（**已有**，返回 `'qi' / 'foundation' / 'core'`）。
2. **步长保不保**：继续 15 游戏分整步、每 tick 168 步，还是金丹改用更粗的步长？
3. **离线配额按什么单位**：
   - 甲：继续 180 游戏天（金丹 = 1.7 现实分钟）——**不建议，等于没有离线**；
   - 乙：3,650 游戏天（金丹 = **34.8 现实分钟**）——现有引擎可跑（136 秒，仍偏卡）；
   - 丙：按现实小时 4.06h（金丹 = **25,550 游戏天**）——体感对，但需要「跨期聚合结算」引擎，
     当前实测约 **16 分钟**。
4. **俸禄 / 秘库 / 老九跟不跟**：是让 90% 挂账跟着时钟加速堆积，还是把**俸禄周期也挂到
   `faction.realSeconds`**（与飞鹰门同一时钟），让「月俸 / 月刷 / 老九」保持同一现实节奏？
5. **探索密度**：168× 下 21 事件/现实秒，继续走 `narrative:'auto'` 全收，还是给金丹单独降事件密度？

**建议**

- **倍率**：按段查表 `{ qi: 1, foundation: 24, core: 168 }`，判据统一改 `realmTierOf()`；
  **步长不动**（15 游戏分），只放大每次 tick 的步数。
- **离线**：**先乙（3,650 天），把「金丹离线只有 35 现实分钟」显式标成已知缺口**；
  聚合引擎落地后再切丙（4.06 现实小时）。不要在没实测的情况下直接写 25,550 天。
- **俸禄 / 挂账**：**统一挂 `faction.realSeconds`**，即「月俸 = 48 现实分钟名义值」，
  金丹不再按游戏年加倍发放。理由：飞鹰门的先例已经写明它**不跟世界时钟加速**，
  90% 挂账又只能在秘库花；两者用两个时钟，必然一边堆钱一边没货。这条要跟 A2 的定价一起看。
- **探索**：不降密度，继续 auto 全收（奖励按游戏时间等比，`leave` 无奖励 ⇒ 分布不变）；
  只把 `Exploration.vue` 的「24× 说明」改成按档位文案。
- **日结**：先上，再加一条开发期计时日志（每 tick 跨天次数 / 内宅日结耗时），
  超过 200 ms 就停手等聚合引擎。

**影响**

- 代码：`plugins/gameClock.js` · `stores/modules/clock.js` · `plugins/offlineSimulation.js` ·
  `stores/modules/offline.js` · `plugins/salary.js` + `stores/modules/salary.js` ·
  `stores/modules/exploration.js` · `views/Exploration.vue`。
- 断言：`verify-idle`（24× 切换 / 离线分段）+ 新增「三档倍率 / 金丹配额」约 8~12 条。
- 会话量：**1.5~2 会话**（倍率 + 离线 + 俸禄三处一起动）。
- 产出登记：**R33 / R34 改写**（离线配额第三档）+ **新记录**（俸禄发放周期若改现实秒）。

### A2. B8-b 的定价轴：封地 / 侍妾 / 回收按「境界段」还是「建筑等级」？（承接 2026-11-02 A1）

**现状**

- 现在真正用二阶计价的只有三处 + 封地：
  - **封地建设**：基础成本 **Lv1 = 0 / Lv2 = 40 / Lv3 = 500 / Lv4 = 1,500 / Lv5 = 10,000 二阶**
    （四栋建筑再乘 `weight`）。
  - **筑基后侍妾**：**6 二阶/位**（= 该位阶 20 个月月饷）。
  - **物品回收基准**：基础价 6/24/96/384/1536 × 30% = **2 / 7 / 29 / 115 / 461 一阶**。
  - **宝匣已重标**：148 / 444 / 2,000 / 7,200 / 23,040 二阶（试运行）。
- 新收入基准（B8-a 之后）：下柱 **833 二阶/月** = **83 二阶现银 + 750 二阶挂账**；
  挂账只能在秘库花；贡献点 **≈690/游戏月**；练气期探索约 **5~6 二阶/月**。
- **B14 又新增了两块价格面**：① 市集固定价（酒 / 丹药 / 法器），
  ② 修炼位 / 藏书阁 / 义庄等新建筑的建设成本 —— 后者并入 B14，但**方法**仍等这条。

**要定的分叉**

1. 物价按境界段定价，在封地上怎么落：**建筑等级 ↔ 境界段**，还是同一等级对所有段同价？
2. 如果按段：Lv1~Lv5 分别归到哪一段？（原建议 **L1 练气初期 / L2 练气后期 / L3 筑基 /
   L4 金丹 / L5 仙朝（未落地）**。）
3. 定价比例用「**整段总成本 = 该段 2~3 个月可支配收入**」还是「每次升级 ≤ 1 个月收入」？
   可支配 = 俸禄现银 + 探索/秘境，**不含挂账**。
4. **B14 市集的固定价**（酒 / 丹药 / 法器）跟不跟同一条轴（练气段和金丹段不同价）？
5. B8-b 只动现有三个二阶面，还是顺手把丹药 / 符箓 / 灵兽的大库价也定了？

**建议**

- **按建筑等级 ↔ 境界段**（否则同一栋楼在练气和金丹两个价，玩家看不懂）。
- 每级成本 = **该段 2~3 个月可自由支配收入**；练气 Lv2 现值 40 二阶 ≈ 0.4 个月现银，**太便宜**，
  建议抬到 **150~250 二阶**；Lv3 归筑基段后同批再算。
- **市集固定价也按段**，和建设价共用同一张「段 → 价格」表；酒/丹药/法器只定基准价，不逐件手填。
- **B8-b 只动现有三个面**；大库价等大库页面（B2）开工再定，避免空表。

### B1. B14 §十六 的 5 条数值（修炼位 / 人口 / 徭役 / 解锁等级 / 库存上限）

**现状**（《模块四》§十六 共 8 条，其中地块布局是纯 UI、炭场数值等 B11、市集价见 A2，
真正卡开工程序的是下面 5 条）

1. **修炼位基础 50（占位）**：626 子嗣人口上限下的 **8%**。现行子嗣模型是**全员每日固定日增**，
   `npm run sim:offspring` 整张校准表（单灵根 5.7 岁筑基 / 81.7 岁金丹 / 352 岁圆满）都按「全员都练」算；
   加名额后这张表要按「名额占比」重算。木屋未建时是否照给 50 也未定。
2. **乡侯府解锁顺序 + 村民人口上限曲线**：无任何数值。
3. **新增 5 栋（酒坊 / 市集 / 藏书阁 / 义庄 / 丹炉）的解锁等级**：无。
4. **徭役需求 = 等级 × 200**：「等级」指**在建建筑等级**还是**乡侯府等级**未定；
   且现有村庄合计 **5,600 人口 / 1,400 可徭役（25%）**，而 **21 栋 × Lv1 × 200 = 4,200 需求**
   —— 数字对不上；MVP 4 栋全 Lv3 也要 2,400，是 1,400 的 1.7 倍（满足率 58%）。
5. **中间产物上限 500 + 人口自然增长 2~3%/年 的具体值**：都是占位。

**要定的分叉**

1. 修炼位基础名额是固定 50，还是挂大境界（626/900/1200/1600 的百分比）？木屋未建给不给基础名额？
2. 村民人口上限曲线怎么挂乡侯府 Lv1~Lv5？徭役需求按单栋还是乡侯府总需求？
3. 新增 5 栋的解锁等级按「先生产 → 后功能 → 再数值」排，具体落在哪几级？
4. 中间产物 500 是「约几天缓冲」？人口 2~3% 取 2.5% 可否？

**建议**

- **修炼位**：基础名额挂大境界 = **子嗣上限的 8%**（626→50 / 900→72 / 1200→96 / 1600→128），
  木屋每级 **+10**；**未建木屋也给基础名额**（否则开局 0 人修炼 = 子嗣系统停摆）。
  这是把「50」从魔法数改成可解释的比例，数值本身不变。
- **徭役**：**放弃「等级 × 200」，回到 v1 的项目固定值表**（修建灵田 100 / 亭卫 200 / 驿站 300 /
  长墙 500，21 栋逐个挂表），再加一条 **同时在建上限 4 个**。理由：固定值已经按工程规模定过数，
  MVP 四栋同时建 ≈ 400~800 需求 ≤ 可徭役 1,400，能跑满速；「等级 × 200」在 21 栋时会膨胀到
  4,200+，和 5,600 人口对不上。
- **人口上限曲线**：乡侯府 **Lv1 6,000 / Lv2 9,000 / Lv3 13,000 / Lv4 18,000 / Lv5 24,000**
  （Lv1 略高于 5,600 现状），增长 **2.5%/年**（约 **28 游戏年**翻倍 = 练气段 11.3 现实天 /
  筑基段 11.3 现实小时）。
- **新增 5 栋解锁等级**：酒坊 **Lv1**（粮的出口，最早）· 丹炉 **Lv2** · 市集 **Lv2** ·
  藏书阁 **Lv3** · 义庄 **Lv3**。
- **中间产物 500**：按「MVP 日耗 ≤ 50 件」估算 = **10 游戏天缓冲**，先保留 500，实测后再调。
- **必跑**：修炼位落地后 `npm run sim:offspring` 必须按名额占比重跑，校准表同步《真值表》§5.7。

**影响**

- 代码：`plugins/estate.js`（人口 / 徭役 / 建筑表）· `plugins/innerCourt.js`（修炼位 + 日增）· `views/Estate.vue`。
- 断言：`verify-estate`（人口/徭役/解锁）· `verify-harmony`（修炼位）。
- 会话量：**1 会话**（纯数值落地），**但 sim 重跑另算**。
- 产出登记：**R53 / R54 数值回填**；修炼位会**减少**子嗣总产出，按规则先登记再重算门槛。

### B2. 大库页面的形态（承接 2026-11-02 B2）

**现状**

- 挂账 90%（下柱 **750 二阶/月**）目前只能买秘库两栏（心法 + 同参底材），**买不到丹药 / 法器 /

- 大库没有代码、没有价格表、没有页面。

1. 大库是飞鹰门页里的一个分区，还是独立页？
2. 结算只用挂账额度，还是「挂账 + 贡献点」双币？
3. 「内部优惠价」= 打几折？（秘库已定 1 二阶 = 1 贡献点）
4. 货架常驻，还是像秘库一样月刷？

**建议**

- **飞鹰门页的分区**（不新增导航）；**只收挂账**；**1 二阶 = 1 点，不再打折**（与秘库一致）；
  **常驻货架、不月刷**（大库是稳定补给，不是抽卡）。
- 商品目录交网页端（《可定稿内容清单-2026-11-02》#05，四类各 5~10 件）。

### B3. 藏书阁：子嗣功法走哪个乘区 + 灵根 ↔ 功法匹配表

**现状**

- 藏书阁是 B14 的第 7 项，规则已定（每子嗣 1 门、不可替换、按灵根匹配、无匹配不学）。
- **但子嗣目前没有功法系统**：模块一硬口径是「非心法效果子嗣吃不到」；桂冈已学功法里
  开局只有 3 本（火 / 土 / 金），木 / 水 / 兽 / 器灵根的子嗣抽不到（**预期行为**）。
- 现有只有 `artCoverage`（灵根覆盖率），**不是**「灵根 ↔ 功法」查表。

**要定的分叉**

1. 子嗣功法加成走哪个乘区：独立乘区加日增？还是并进 `offspringTraitBonusOf` 的软上限？
2. 匹配表怎么建：按功法 `element`（五行 / 兽 / 器）↔ 子嗣灵根，1:1 硬匹配？
3. 是否受 `ART_GRADES` 品阶影响？数值给多少？

**建议**

- **独立乘区**：子嗣修炼日增 `× (1 + 功法加成)`，**不进突破门槛**、不与桂冈非心法效果混算。

**影响**：**1 会话**（新系统，含 `sim:offspring` 复算）；`verify-harmony` 新增 5~8 条；
产出登记 **R54 追加**（子嗣修炼速度 +，先登记再算门槛）。
