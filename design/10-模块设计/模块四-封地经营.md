## 一、模块定位与三层解耦

封地经营是放置游戏的核心产出引擎。三层解耦：

层 谁 管什么 操作频率 入口

巡视层 桂冈 进度条加速（仅巡视时段 ×2） 每天（主循环第一环） 主界面「桂冈的一天」

徭役层 封地人口 建设进度、民心维护 拖拽调整（低频） 封地独立页「徭役」页签

管理加成层 子嗣 家族工作产出 偶尔调整 内宅「家族工作」页签

巡视不是产出动作，是加速动作。 桂冈巡视时，所有进度条（建设/征收/产出）速度 ×2；不巡视按正常速度走。
**2026-10-27 澄清**：×2 只覆盖**巡视时段本身**（当天 06:00 → 06:00+S，S=1 或 2 小时），
**不是「当天巡视过就整天 ×2」**。日结按 `(24 + S) / 24` 折算：S=2 → +8.3%、S=1 → +4.2%。

### 3.2 徭役分配：**先开工的优先，逐项分配**（2026-11-04 修订）

> **2026-10-26 A3 #5 拍板**：MVP 不做拖拽分配。
> **2026-11-04 修订**：**「全体均分」作废** —— 它让所有项目共用一个满足率，
> 总需求 > 2×徭役时全体 <50%，于是所有项目同时停工、谁都完不了工 ⇒ 需求永不下降 =
> **永久死锁**（实测 4 个 Lv4 升级 / 3 个 Lv5 升级即可触发，且当时没有取消入口）。

**徭役需求 = 目标等级 × 200**（v2）：Lv1 = 200，Lv5 = 1,000。

· 按**开工先后**（`job.seq`）逐项发徭役：先开工的项目先拿满，剩下的依次往后发。
· 单项满足率 = `分到 / 需求`，**≥50% 才开工**；50%~99% 按这个比例线性减速。
· 够不到 50% 的项目本轮**排队**：分到的徭役退回池子（**不占着**），前面的项目完工后自动接上。
· 因此**只要总徭役够第一个项目的 50%，就永远有项目在推进** —— 结构性死锁不存在。
· 老档的 job 没有 `seq` ⇒ 按 `builds` 的插入顺序兜底（与开工先后一致）。
· 拖拽排序（玩家手动调优先级）仍是**第二批**内容；MVP 的默认优先级 = 开工先后。
· 真源：`plugins/estate.js` 的 `laborPlanOf`（逐项分配）/ `laborSatisfactionOf`（概况展示，不再参与推进）。

人口变化时：

· 总人口变化（战争/新生/迁移/灾害）→ 徭役人口、农业人口、非劳动力人口成比例变化。

· 项目内徭役也成比例变化 → 满足率跟着变。

### 11.2 工程口径（代码里必须一致）

- **成本单位**：设计表是**二阶灵石**，代码账本 `currency.spiritual` 是**一阶整数** ⇒ `× 100`。
  例：灵田 Lv2 = 40 × 0.9 = 36 二阶 = **3,600 一阶**。
- **工期**：`基准月 × 权重 × 30 天`，**按天推进**（§10.5 的「每月 +1/工期」折算到天）。
  例：灵田 Lv2 = 4 × 0.9 × 30 = **108 天**。
- **首建**（2026-10-26 拍板）：**0 成本**，工期 = 该建筑 Lv1→2 的 **50%**（灵田 54 天）。
  首建判定看 `buildings[id]` 是否存在 —— 只对「从无到 Lv1」生效，不会被反复利用。
- **付款**：进度推多少就付多少（按剩余成本等比），完工时补齐尾款 ⇒ **总付款恒等于总成本**；
  灵石不足当天停工（进度冻结），补上后继续。单项徭役分到不足 50% 则**排队**
  （不占徭役，前面的完工后自动接上）。
- ~~**民心**：先向基准靠拢（`2×乡侯府等级`/天），再用**靠拢后**的民心算当天的产出 / 税收 / 徭役效率。~~
  **v2 作废**：代码里这段仍存在（`estate.js` 的 `moraleCoefficientOf`），B14 一并删除。
- **征收**：进度条按 0~100 存，`100/30 × (24+S)/24` 个百分点/天；满格且本月未收过才入库
  （`taxCollectedMonth = floor(settledDay/30)`），入库后归零。
  **本月已收过就停止积累** —— 不把一管满格条攒到下月（§10.2「提前满不叠下月」）。
- **结算归属**：日结的是「**刚结束的那个日历日**」（`settledDay = midnight/86400 − 1`），
  所以第 1 次日结的日志是 `day: 0`（UI 显示第 1 日），月份也按这个日算。
- **日初等级快照**：产出与税收都读**日初**等级 —— 今天完工的灵田今天不产、乡侯府今天升到 Lv2
  今天也还不收税，全部从**次日**生效。
- **巡视加速的判定（2026-10-27 改）**：只在**巡视时段**（当天 06:00 → 06:00+S）内 ×2，
  日结按 `(24+S)/24` 折算。**旧的「`patrolEndSeconds` 落在当日窗口就整天 ×2」作废** ——
  它让几乎每天都是巡视日，×2 实际常驻，与「只有巡视期间才加速」不符。
  探索 / 秘境时 dayLoop 冻结、当天没巡视 ⇒ 折算系数 = **1**（预期行为）。
  ⚠ 这是**收益减少**（×2 → ×1.04~1.08），已登记 R04；B3 的封地数值按此修正，**不重算突破门槛**（封地产出不进门槛）。
- **幂等**：`lastDay` 记录已结算到第几个游戏天；同一天重复调用直接返回。异常跨多天只结一天。
- **存档**：新增顶层 `estate` 对象，靠 `deepMerge` 补默认值，**不升 `SAVE_VERSION`**（不匹配会清档）。
  内部一律用对象（深合并不补数组元素），只有 `log` 是数组且由 `normalizeEstate` 兜底。

> `3×(阶−1)+品序` 的实际上限是 **12**（T4 极品），15 只是归一化分母。
> 按公式字面实现，**T3 极品 = 9 → 1.06**（这是现实锚点，×Lv3 = 1.166）；
> 若把分母改成 12，T3 极品会变成 1.075，与 §13.10 的 1.166 冲突。
> 所以保留 `/15`、把上限写实为 1.08。

- **不复用** `artEffects.artEffectCoefOf`（`1.12^score` = 1.0~3.9）：那会让校准表大面积失效。
- **线性映射，不按 tier 分档**（用户 2026-11-05 确认）。

### 13.5 传功阁等级倍率（A4，2026-11-05）

```
等级倍率 = 1.0 + 0.05 × (传功阁等级 − 1)
```

| 等级 | Lv1 | Lv2 | Lv3 |
|---|---:|---:|---:|
| 倍率 | 1.00 | 1.05 | 1.10 |

- **实时读当前建筑等级、不存快照**：升级立即生效，不用重抽，老档零迁移。
- 等级**不**解锁更高品阶：池子已受「桂冈已学」限制，再加一层闸门会变成双重锁。

### 13.6 触发时机与幂等（A5 + 2026-11-05 补）

| # | 场景 | 规则 |
|---:|---|---|
| 1 | **传功阁落成**（首次建成 Lv1） | 给**当时在世、有灵根、还没学过**的全体子嗣抽一次（含已筑基 / 金丹） |
| 2 | **之后出生的子嗣** | 出生不抽；**到筑基那天**（`realmLevel` 首次 ≥ 11）抽一次 |
| 3 | **已学过的人到筑基** | **不抽**（不可替换） |
| 4 | **落成时已筑基 / 金丹、但没匹配到** | **2026-11-05 补**：桂冈每学会一本**新**功法，对「有灵根、未学、`realmLevel ≥ 11`」的人再抽一次（池子变大才有意义） |
| 5 | **老档补抽** | **2026-11-05 补**：读档时若传功阁等级 ≥ 1 且从未结算过，**等价于「落成」**，对全体未学者抽一次（存量子嗣不能因为楼是早先建的就没功法） |

- 全部走**幂等**：同一子嗣同一次触发不重复抽。
- ⚠ **落代码时的实现口径（2026-11-05）**：#2 的「到筑基那天抽一次」按**事件**实现成
  「结算前后跨过 `realmLevel 11` 且还没学 → 抽一次」，**不区分出生在落成前还是后**。
  效果上：落成时没匹配到的练气子嗣，到筑基那天会多一次同池抽卡机会（最多一次，
  不改成每日扫描）；若要严格只给「落成后出生的人」，需要额外记出生批次，暂不做。
- 触发是**事件式**的（落成 / 首次到筑基 / 学会新功法 / 老档首次结算），
  **不是**「每天看一次谁还没学」—— 后者会在池子变大后变成「早晚必中」，违反「没匹配不兜底」。
- 触发点放在 `advanceInnerCourtDay` 里**打坐 + 历练都结算完**之后统一判一次：
  `realmLevel` 有 3 条写路径（纯打坐 / 子嗣历练 / 读档回填），只挂在打坐循环里会漏掉历练突破的人。

### 13.7 完整公式与基准 k

```
功法系数 b = (1.0 + 0.10 × score / 15) × (1.0 + 0.05 × (传功阁等级 − 1))   → 1.00 ~ 1.188

子嗣日增 = 2 × 1.2^(层−1) × k × 灵根系数 × (1 + 配给同参) × (1 + 灵地) × (1 + 词条) × b

k = 0.80（2026-11-05 落代码确认）
```

- **`k = 0.80` 是全局基准下调**：没建传功阁、没匹配到功法的子嗣**也一起慢 19%**。
- 净系数 **0.80 ~ 0.9504** ⇒ **任何子嗣都回不到 k=1.0 时代的速度**；传功阁是「回补」不是「净增益」。
- 这是保住「三灵根金丹无望 / 五灵根死也筑基不了」的代价：`k=1.0` 时三灵根 204 / 1.188 ≈ 171.9 岁就能金丹。
- `k` 的最终值由 `npm run sim:offspring -- --art=` 跑出实际 `b_avg` 后校准（粗估 0.78~0.85）。
  **2026-11-05 结案 = 0.80**：`k` 的约束是**最坏档**（三灵根 + T3 极品 + Lv3，`b = 1.166`），
  `k ≤ 204.3 / (200 × 1.166) = 0.876`；取 0.80 留 11 岁余量。
  `b_avg` 只决定「平均体感」，不改变定性结论 —— 开局池只有火/土/金三本，多数子嗣 `b = 1.0`，
  实际平均净系数 **低于** 0.84，正是设计想要的保守方向。

### 13.8 五灵根

**正常参与传功阁，不做特殊限制。**

- 验算（k=0.80、T4 极品 + Lv3 净 0.9504）：五灵根 142 / 0.9504 = **149.4 岁 > 120 岁寿元** ⇒ 定性保住。
  （现实档 T3 极品 × Lv3 净 0.933 更慢，结论只会更强。）
- 校准表按「假设所有人都有修炼名额」的**假想基线**算（五灵根实际通常拿不到名额，更安全）。
- 不做「五灵根不参与」或「功法加成打折」。

### 13.10 预期行为 / 已知边界

- **全局慢 19%**：见 §13.7，不是 bug。
- **1.188 是算术上限、现实到不了**：传功阁三级要乡侯府 Lv3 才能建满，而 T4 功法是元婴档（元婴未落地）
  ⇒ 实际最高 ≈ **T3 极 × Lv3 = 1.06 × 1.10 = 1.166**。
- **开局 3 本导致部分灵根抽不到**：等桂冈学新功法缓解，见 §13.3。
- **五灵根的定性由修炼位兜底**，不是靠 `k`：五灵根排不进修炼位就不涨修为（《真值表》§5.7）。

## 十四、修炼位（快子峰木屋，2026-11-02 新增）

| 项 | 值 |
|---|---|
| 基础名额 | **50**（2026-11-03 用户拍板：**刻意稀缺**，不提高） |
| 每级增加 | **+25/级**（木屋最多 3 级 ⇒ 50 / 75 / 100 / **125**）—— 2026-11-04 按真实档重标（旧 +10/级 ⇒ 满级 80 只覆盖 115 名有灵根子嗣的 70%） |
| 排序依据 | 灵根系数降序 → 当前境界降序 → 出生早 → id（后两条只为结果稳定） |
| 木屋未建时 | **基础 50 照给**（2026-11-04 用户拍板） |
| 超出名额 | **当日不涨修为**，不攒不补 |
| 历练出去的 | **不占名额**（修为由历练结算） |
| 满级（金丹十层） | **不占名额**（再练也不会涨） |

**影响面**：

- 加修炼位后，`npm run sim:offspring` 的校准表（5.7 岁筑基 / 81.7 岁金丹…）只对
  **拿到名额的那批人**成立；超出名额的子嗣进度会停在某一天。名额按资质排 ⇒
  在练的是灵根最好的那批，所以单 / 双灵根那几行才是大多数人的真实进度。
- 626 人口上限下，基础 50 = **8%** 的子嗣能练。这是 2026-11-03 拍板的**刻意稀缺**；
  **满级 125 在金丹期（600+ 子嗣）仍只覆盖约两成**，稀缺感保留。
- 与「子嗣词条 / 同参配给」的关系：修炼位只决定**谁练**，词条与同参仍按各子嗣自己算。
