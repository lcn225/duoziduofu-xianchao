## 一、基础规则

| # | 项 | 口径 |
|---:|---|---|
| 1 | 离线上限 | **按相位三套，单位 = 现实时长 T = 4.8 小时**：练气 **180 天**（= 4.8h）/ 筑基 **4,320 天** / 金丹 **30,240 天**（2026-11-11 R34 已抬到目标态）。超出部分不结算；**世界日历也只推进结算的天数** |
| 2 | 结算效率 | **100% 平**，不递减 |
| 3 | 配置来源 | **沿袭下线瞬间**的配置（桂冈日常队列 / 百艺排班 / 封地建设 / 子嗣历练策略），不需要额外的托管设置 |
| 4 | 时间换算 | 练气期：**96 现实秒 = 1 游戏天**（`SECONDS_PER_GAME_HOUR = 0.25`）⇒ 1 现实小时 = 37.5 游戏天。**筑基后 24×**：**4 现实秒 = 1 游戏天** ⇒ 1 现实小时 = 900 游戏天。**金丹 168×**：**0.571 现实秒 = 1 游戏天** ⇒ 1 现实小时 = 6,300 游戏天 |
| 5 | 月长度 | 1 游戏月 = 30 天 = **48 现实分钟是名义值（完全不睡）**；实际因睡觉加速约 **34~42 分钟**（见《时间系统》§2.1） |

> **为什么上限的基准是 4.8 现实小时**：原则 A =「离线等价于同样现实时长的在线挂机」。
> 4.8h 是练气现状（180 天），沿用它可以不动练气节奏；筑基 / 金丹按各自速率折算成
> 4,320 / 30,240 游戏天。三段的「离线价值」因此一致，24× / 168× 不会被离线上限吃掉。
> T 本身**不是**性能权宜 —— 180 天当初才是（2026-10-26 为了 7.9 秒的结算耗时）。
> B1 把两件事分开了：**T 是设计值，限速的是 R34 之前能承受的结算耗时**。
>
> **游戏天从哪来**：上限的**单位**是现实时长，游戏天是各段换算的**结果**
> （`T ÷ 每游戏天的现实秒`）。世界日历仍只推进结算过的天数 —— 这是实现性质，
> 不是上限单位，别再拿它当「按游戏天封顶」的理由。
>
> **为什么不做效率递减**：旧方案（8h 内 100% / 24h 内 90% / 2 天 80% / 3 天 70%）
> 是在「上限 3 天」的前提下设计的；上限压到 12 小时后，递减只会变成惩罚。
> **收益减少要登记**——本版不做递减，所以不涉及。
>
> ✅ **2026-11-11 R34 落地后，上限就是设计值**：筑基 4,320 / 金丹 30,240 游戏天，
> 与在线同等现实时长。旧的「金丹挂一晚只收 14.3 分钟」是过渡期缺口，**别再写回文案或预期**。

## 二、特殊事件（防呆与防死锁）

| 事件 | 离线处理 | 理由 |
|---|---|---|
| **封地告急**（妖兽入侵等） | **冻结封地**：不产出、不消耗、不推进时间。报告高亮提示，上线处理后才恢复 | 封地是全局资源源，继续跑会放大错误。⚠ **MVP 无对象**：告急在 P38 MVP 已关停（《模块四》§6.2），封地上线后本行才有东西可冻结 |
| **子嗣陨落** | **停住，上线弹窗** | 不可逆 + 有【修行返还】，不能替玩家决定。**这是唯一的暂停点** |
| **子嗣诞生** | 自动取名、**不使用洗命符** | 洗命符是手动道具，离线不消费 |

> **侍妾下毒 / 生气 / 回娘家**：**2026-10-25 砍掉**（只存在于《模块八》事件卡，代码未实现）。

## 三、结算算法（防卡顿）

**绝对不能按秒 / 按小时循环** —— 离线 12 小时 = 43,200 游戏小时，前端会卡死。
必须按**游戏天切片**：

```
1. offlineRealSeconds = now − lastSaveRealTime
2. 预算 = offlineRealSeconds 的现实秒；按相位分段（P55-c）：
   · 当前境界 → 相位（练气 / 筑基后）：`offlinePhaseOfLevel(level)`
   · 本段天数 = min(剩余预算 ÷ 该相位每游戏天的现实秒, 该相位剩余配额)
     练气 96 秒/天 · 配额 180 天；筑基后 4 秒/天 · 配额 4,320 天；
     金丹 ≈0.571 秒/天 · 配额 30,240 天（2026-11-11 R34 目标态）
3. 用本段天数的终点调 `runOfflineSimulation` 的**同一个入口**，按**块步长**循环
   （练气 1 天 / 筑基 7 天 / 金丹 180 天，`OFFLINE_TUNING.blockDays`，2026-11-11）——
   每一块**调各模块自己的推进函数**，线性产出按块长折算，不另写一套结算：
   · 桂冈日常（按§三.1 的三选一）：**块首完整跑 1 天，其余天按「一天产出模板」逐天补发**
     （`applyOfflineDayTemplate`，材料与药力照常扣、突破即停）
   · 封地税收 / 灵田产出（**块内仍逐日算**，仓满刹车与月税不能简单乘天数；
     复印 / 钱袋 / 落盘合成块首块末各一次，P62 步骤 1）
   · 药浴池转换（块末一次）
   · 侍妾怀孕 / 子嗣出生（按块末判定）
   · 灵力 → 修为（按天模板补发，不逐 tick）
   · 百艺成品（按天模板逐天重放，缺料照常停工）
   · 子嗣修炼 / 子嗣历练 / 家族工作（全量，按块长折算）
4. 本段跑完再看境界：**变了**（离线期间筑基）⇒ 剩下的预算按新速率换算，回到第 2 步；
   **没变** ⇒ 预算或配额已经用尽，结算结束。报告用 `phases[]` 记下每一段的天数
5. 中断：某天触发「子嗣陨落」→ 立即停止后续天数，标记待处理
   （「封地告急」本轮**无对象**，见 §二 与 §七）
6. 汇总：灵石、材料、宝匣、子嗣出生、讣告、修为与突破、重大事件
```

> **为什么必须分段而不是按最终境界一刀切**：下线时练气、离线第 100 天筑基的话，
> 按最终境界算会把整段离线都当成 4 秒/天，等于白送 20 倍收益；按最初境界算又会
> 让破境后的玩家少拿。分段 = 「练气段烧掉 100 天 × 96 秒，余下的现实秒按 4 秒/天 换」。

- 纯函数，不碰 store；返回值交给 store 一次性入账。
- 掉帧跨多个月由 `checkBoundary` 补触发的老问题不在这里 —— 离线是**独立读档入口**。

### 3.1 三大挂机：**严格三选一**（2026-10-26 B1 定）

桂冈离线时不可能同时镇守、探索、秘境。读**下线瞬间的状态**：

| 下线时在 | 离线跑什么 |
|---|---|
| **镇守** | 日常循环（练功 / 炼体 / 百艺 / 互动） |
| **探索** | 探索事件结算（含叙事 20 秒自动善意） |
| **秘境** | 按天切片跑秘境挑战（一趟 `ceil(层数/10)` 天） |

**子嗣独立**：子嗣的**历练与家族工作全量参与**，不受桂冈三选一影响 ——
它们本来就是日结的。家族工作里的经济产出照常入库。

### 3.2 突破：满足即突破（2026-10-26 B1 定）

- 修为到当前境界上限、且**契合度 × 灵地都达标** → **自动突破**，与在线同一函数
  （`core.tryBreakthrough`）。突破结果进报告汇总。
- **不达标就锁死**：修为卡在 **100% 不溢出**，报告高亮「修为已满，请上线更换功法 / 同参 / 灵地」。
- **不做「替玩家换配置」**：换功法 / 同参是玩家的决定，离线只执行已有配置。

### 3.3 资源落账：与在线完全一致

| 类 | 离线处理 |
|---|---|
| **宝匣** | **不自动开**，进 `inventory.chests`（开箱是玩家操作） |
| 灵石 / 材料 / 残页 | 直接进背包，沿用在线获取逻辑 |
| 子嗣诞生 | 自动取名、**不用洗命符**（洗命符是手动道具） |
| 侍妾 / 子嗣寿终 | 聚合进报告【内宅讣告】，见 §四 |

### 3.4 讣告必须聚合

12 现实小时 = 450 游戏天 ≈ 凡人一生。寿终会有**几十条**，报告**不能逐条列**：

> 内宅讣告：妻妾 **X** 人、子嗣 **Y** 人已寿终正寝（已移入家族树）。[查看名单]

名单点开再看逐条（按辈分 / 生母分组），不进主报告。

### 3.5 粗颗粒度块结算（2026-11-11 落地，取代「金丹周结算」草案）

> 用户拍板：**离线结算不需要那么精确，用粗颗粒度换速度**。真源 `OFFLINE_TUNING.blockDays`。

| 项 | 值 |
|---|---|
| 块步长 | 练气 **1 天** / 筑基 **7 天** / 金丹 **180 天**（R34 实测倒推：30 天 136 秒 → 90 天 77 秒 → 180 天 54 秒） |
| 块内一次算 | 内宅日结（修炼 / 家族工作 / 繁育 / 历练）、药浴池转换 |
| 块首跑一次 | 桂冈日常循环**完整跑 1 天**，产出记为「一天模板」（练功小时 / 炼体轮 / 百艺轮 / 互动人数） |
| 其余天补发 | `applyOfflineDayTemplate`：**块内 N 天一次批量**（阶段 D2，§3.8）—— 修为 / 灵兽同修 / 炼体轮 / 百艺 / 晚间互动按 `k` 天折算，**材料与药力照常扣**（缺料照常停工），**突破即停**；回滚开关 `OFFLINE_TUNING.dayLoopBatch` 退回逐日重放 |
| 仍逐日 | 封地（仓满刹车 / 月税） |
| 近似口径 | 子嗣**诞生**按块末判定（最多晚一个块长）；**凡人寿终**自 P62 阶段 C 起按真实死亡日（§3.7），修士寿终仍块末；药浴池块内看到的是块初药力；繁育按 `1−(1−p)^days` 折算受孕概率；日常循环的日间波动（某天体力不足 / 临时打断）被抹平 |
| 实测（真档 1,436 子嗣 / 4.7MB） | 1,500 天：逐日 **214 → 14.8 秒**；目标态 30,240 天：**54 秒** |

> **收益总量基本不变**：线性产出（修炼 / 家族工作 / 历练修为 / 百艺 / 炼体）按天重放，
> 期望一致；变化的是**时间点与顺序**（谁先死、谁先结婚、哪一天生的）。属于「收益不变、精度下降」的性能改动，
> 不触发宪法第二章门槛重算。⚠ 这是**有意为之的近似，不是 bug**。
>
> 离线**上限**从过渡值 1,500 抬到目标态 4,320 / 30,240 是**收益增加**（金丹离线价值从
> 14.3 现实分钟变成 4.8 现实小时），已登记《产出登记表》R34。
> 原「金丹周结算（4,320 周）」草案不再采用 —— 块长 180 天已覆盖，且不依赖 B17-b 周引擎。

### 3.6 封地延迟账户与凡人四类产出落点（2026-11-13 · P62 阶段 B）

**封地延迟账户（「当天收入次日可用」）** —— 真源 `estate.advanceEstateBlock`。

| 项 | 口径 |
|---|---|
| 块内记账 | 块首读一次钱袋，块内只维护本地 `stones`（= 当天可用的钱），**不逐日写钱袋** |
| 每天 | 建设预算只从当天可用余额扣；当天经营链 / 税收 / **凡人岗位灵石**收入在日末才并入余额 |
| 块末 | `currency.spiritual = 当天可用余额`。⚠ **不是「期初 + 全部收入」** —— 最后一天的预算会算错 |
| 等价性 | 与逐日路径**逐位相同**（`verify-estate`：12 天快照比对 + 「刚好靠昨天收入才付得起」专项） |

**凡人岗位四类产出落点**（`advanceFamilyJobs` 的 `secular / spiritual / herbs / forgeItems`）：

| 产出 | 落点 | 理由 |
|---|---|---|
| 现银 `secular` | **直接入账** | 不参与建设预算，无时序依赖 |
| 灵植 `herbs` | **块末入背包** | 药浴唯一料路；块内时点偏一个块长，总量不变 |
| 法器 `forgeItems` | **块末入背包** | 块内无人消费，推迟无害 |
| 灵石 `spiritual` | **封地块结算之后**入账 ⇒ **下一块的第一天才能花** | 与封地延迟账户同一口径（`deferSpiritual`） |

> ⚠ **这是有意为之的块粒度近似，不是 bug**：阶段 D2 落地后**仍然保持这两个块末落点** ——
> 材料账本（§3.8）要求「块内背包材料只减不增」，灵植若块内逐日到货就会破坏这个不变量；
> 灵石同理，封地块的钱袋是整块一次结算。当前**总量零损失**，只有时点最多偏一个块长
> （练气 1 天 / 筑基 7 天 / 金丹 180 天），最后一块的产出留在背包 / 钱袋里等下线上线。
> 落点顺序的断言见 `verify-offline`（「封地块结算时看不到本块凡人灵石 / 下一块才拿得到」）。

### 3.7 活跃索引与凡人收尾结清（2026-11-13 · P62 阶段 C）

> 内宅原来是**每块 6 遍全扫**（修炼 / 历练 / 传功阁 / 寿终 / 繁育 / 家族工作），
> 1,436 子嗣 × 168 块就是瓶颈。阶段 C 改成「重放开始扫一次建桶，之后每块只扫相关的桶」。
> 真源：`plugins/innerCourt.js` 的 `buildOffspringIndexOf` / `blockWorkDaysOf` /
> `familyJobBlockOutputOf`；store 侧 `beginOfflineCourtIndex` / `endOfflineCourtIndex` / `offlineCourtAliveCountOf`。

**桶的口径**（建桶时按重放**起点**判定，块间成员不变 —— 离线不分配新岗位、不配置新历练、不新增修炼位）：

| 桶 | 条件 | 谁扫它 |
|---|---|---|
| 修士桶 | 有灵根 + 在世 | 修炼 / 传功阁跨线 / 寿终（修士） |
| 历练桶 | 配了历练（非「仅打坐」）**或**养伤中 | 历练结算与养伤倒计时 |
| 繁育桶 | 男性 + 在世 + 已婚，**或**到点队列（`youngMales`，按婚配到点时刻升序，块内到点挪进来） | 繁育 |
| 在岗桶 | 有岗位 + `canDoFamilyJobOf` | 家族工作 |
| 凡人事件线 | 无灵根 ⇒ 境界不会变 ⇒ 寿元可预计算 | 寿元预告（90%）与寿终 |
| 已故 | `fallen` / `passed_away` | 任何扫描都不进 |

**凡人收尾结清（C4）** —— 这是本阶段唯一改到「算多少」的地方，方向是**更准**，不是更少：

| 项 | 口径 |
|---|---|
| 死亡日 | **出生 + 寿元**（`offspringDeathSecondsOf`），块内到期就判死；不再一律推到块末 |
| 家族工作 | 块内死了的只结**存活天数**（`blockWorkDaysOf` = 死亡前的 00:00 个数），与逐日路径逐位一致 |
| 繁育 | 本块内刚死的仍按存活天数折算受孕概率；**不给死人在块末办婚配** |
| 修士寿终 | 寿元随突破实时同步，**仍块末实时判**（C6），不能预计算 |
| 死亡时刻 | `passedAwayAt` 写**真实到期日**（不再写块末），讣告年龄 = 寿元整数 |

**人口增量（C5）**：`index.aliveCount` 建桶时算一次，之后按「新生 +1 / 寿终 −1 / 秘境陨落 −1」增量维护，
块末传一次给 `advanceEstateBlock({ offspringCount })` —— 封地不再逐日全族 filter。
封地块内人口整块不变（内宅已按整块结算完），与逐日读 getter 的值相同。

**边界与注意**：

- 索引是**模块级变量，不进 Pinia state**（1,436 条子嗣引用进响应式会拖慢重放）；
  只用 action 读，**不能写成 getter** —— Pinia 的 getter 是 computed，非响应式变量会被缓存成首个值。
- 新生子嗣要**立刻进索引**（`deliverOffspring` / `deliverGrandchild` 都会调 `noteOffspringBornInIndex`），
  秘境陨落走 `markOffspringFallen` 出索引。
- 死掉的人**不从桶里删**（各消费方自带在世判定），这样「本块刚死」的还能按存活天数结最后一块工钱。
- 断言：`verify-harmony`（桶划分 / 死亡线 / 存活天数 / 家族工作结算，27 条）+
  `verify-offline`（索引开合 / 人口下传 / 收尾结清 store 集成，18 条）。

### 3.8 材料账本与块内批量日常循环（2026-11-13 · P62 阶段 D）

> 阶段 C 之后剩下的两个热点：**封地 / 百艺每天全背包 filter + sort**（真档 4,500+ 条），
> 以及**日常循环块内 179 次逐日重放**。D 段把它们分别换成「账本索引」与「N 天一次批量」。
> 只改「怎么算」不改「算多少」：在线路径一行不动，产出与逐日路径逐位等价（有断言）。

**D1 · 离线材料账本** —— 真源 `plugins/arts.js`（`beginOfflineMaterialBag` /
`takeOfflineMaterialUnits` / `endOfflineMaterialBag`）。

| 项 | 口径 |
|---|---|
| 建账本 | 每个**镇守块**块首扫一次背包，灵植 / 灵材按 `type` 分组、组内按「阶 → baseId → id」排好（与在线配平顺序逐位一致） |
| 块内 | `planMaterialsOf` / `craftableCountOf` 自动走账本索引；百艺 / 乡间自动百艺 / 药浴扣料只改账本计数，**背包当场不动** |
| 块末 | `endOfflineMaterialBag()` 汇总真正吃掉的量，`takeUnits` 一次性写回背包 |
| 不变量 | **块内背包材料只减不增**：自动百艺成品是丹药 / 法器（不是材料），不进账本；凡人岗位灵植按 §3.6 块末入包，**下一块才看得见** |
| 不开账本的场合 | 探索 / 秘境线（背包会进料，不满足不变量）；回滚开关 `OFFLINE_TUNING.materialBag = false` 退回每天全扫 |

**D2 · 块内 N 天一次批量** —— 真源 `stores/modules/dayLoop.js` 的 `applyOfflineDayTemplate`。

| 环节 | 批量写法 | 边界 |
|---|---|---|
| 修为 | `k = min(N, 到封顶所需天数)`，一次 `cultivate(模板修为 × k)` | **突破当天收尾**，这是唯一失效条件；卡契合度门槛时修为封顶、天数照走 |
| 灵兽同修 | 模板经验 × k；前 k−1 天与最后一天分开推进 | 灵兽等级上限按桂冈境界，与逐日版对齐 |
| 炼体 | 总轮数 = `k × 模板轮数`，**逐轮结算** | 药力一轮一轮吸，料不足自然封顶（与逐日一致） |
| 百艺 | `advanceArtDays(kind, 每天工时 × k)`：进度与扣料在内部逐天走 | 缺料那天照跑不涨进度；账本生效时配平结果可缓存（材料只减不增） |
| 晚间互动 | `runDayEvening(模板次数 × k)` | `pickAutoWives` 自身体力封顶，总人次与逐日版一致 |

- **块首重锚（顺带修复 R34 遗留）**：`rebaseOfflineDayLoop` 在每个块首把日常循环模型的
  `lastSeconds` 拉回块起点。不重锚时，上一块只跑了 1 天、模型落后 `blockDays−1` 天，
  下一块的 `stepDay` 会按 **128 次阶段转换保险丝**静默按 ~9 天记账，这批产出又被当成
  「一天模板」乘出去 ⇒ 离线镇守产出被高估一个量级（金丹 180 天块最明显）。
  重锚后每块正好「1 天完整模拟 + `blockDays−1` 天模板」；练气块长 1 天不触发，保持原路径。
- **回滚开关**：`OFFLINE_TUNING.dayLoopBatch = false` → 退回 `applyOfflineDayTemplatePerDay`
  （2026-11-11 的逐日重放），产出等价、慢一个量级。
- **断言**：`verify-arts`（账本配平 / 扣料 / 释放 + `advanceArtDays` 与逐日逐位等价，24 条）·
  `verify-offline`（块内背包不动 / 块末写回 / 开关回滚 + 批量突破切分 / 回滚开关 / 块首重锚，27 条）。
