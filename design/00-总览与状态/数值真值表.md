### 0.3 三条必须先钉死的账

**① 你给的 Sheet 2 公式有一处代数反了。**

原式：

```
实际修为上限 = Base × (1 + Child + Other)
综合修炼速度 = Land × (0.5 + Fit×1.5) × Fate × spiritRate × (1 + Child)
```

两式相除，子嗣项**不会完全对消**：

```
耗时 = T0 × (1 + Child + Other) / (1 + Child)
     = T0 × (1 + Other / (1 + Child))
```

后果有两个，方向都反了：

- `Other` 越大，突破**越慢**（其他加成变成了惩罚）；
- 子嗣越多，`Other` 的拖慢**越小**，但永远不可能加速。

这与「子嗣只让数字变大、不改突破时间」的设计意图不符。**本表采用修正版：**

```
Cap_eff = Base × K × (1 + Child)                 // 子嗣只膨胀上限
R       = Land × (0.5 + Fit×1.5) × Fate × spiritRate × Bandwidth
          × (1 + Child) × (1 + Other)            // 子嗣同时膨胀速度
耗时    = Cap_eff / (R × k) = Base × K / (…)     // Child 精确对消
```

结果：**子嗣数量对突破时间的影响 = 0；`Other` 是真正的加速项。** 这正是你要的「肝帝看着爽、节奏不崩」。

**② 宪法第二章的「累计」列不能简单相加。**
它只列了 8 个**锚点**，中间还有 L4/L5/L7/L8/L9/L12/L13/L16/L17 等未列出的级。
把 8 个「目标现实时间」直接相加会得到 113 小时，而累计列写的是 8.9 天 —— 差的正是这些中间级。
按「锚点逐节点 + 中间级几何插值」重建后：L6 37.4 分钟（表 38）、L10 272.5 分钟（表 283）、
L14 31.9 小时（表 33）、L18 8.85 天（表 8.9）—— **全部吻合**。
所以第二章是自洽的，**读法是「逐节点目标 + 插值」，不是「把表里的数字相加」**。

**打坐转化率的来源**（`cultivationMath.js`）：
每次打坐消耗 `floor(10 × 1.5^(L-1))` 灵力，获得 `floor(1 × 1.2^(L-1))` 修为，
30%×luck 概率本次翻倍。所以：

```
k(L) = 1.2^(L-1) / 1.5^(L-1) × (1 + 0.3×luck)
     = 0.8^(L-1) × 1.3
```

⚠ 这个 0.8 的指数是**后期变慢的主刹车**：L18 时 0.8^17 = 0.0225，即 1 点修为要 44 点灵力。
它比灵地产出涨得慢，所以后期必须靠 `K` 抬门槛。

### 2.2 公式（本表采用，已修正）

```
① 灵力产出（全天等效，现实秒）
R(L) = Land(L)
     × (0.98 + 0.32 × Fit)
     × Fate_Coef
     × spiritRate
     × Bandwidth
     × (1 + Child)
     × (1 + Other)

② 打坐转化率
k(L) = 0.1 × 0.8^(L-1) × (1 + 0.3×luck) × Shrine

③ 修为产出
e(L) = R(L) × k(L)

④ 实际修为上限
Cap_eff(L) = Base_Exp(L) × K(L) × (1 + Child)

⑤ 突破耗时（现实秒）
Time(L) = Cap_eff / e
        = Base_Exp × K / [Land × (0.98+0.32Fit) × Fate × spiritRate
                          × Bandwidth × (1+Other) × k(L)]
```

> ✅ **2026-10-19 口径已统一**：代码速度项是 `0.98 + 0.32×Fit`（《模块一》§5.1），
> 本表的公式与 §2.4 的 `K` 都已按它重算（K 范围 **0.907~2.209**）。
> 旧版「`0.5 + 1.5×Fit` + 新速度项两套不要混用」的警告作废。
> 算突破时间直接用本表公式 + §2.4 的新 K，不要再拿旧 K。

**⑤ 里没有 `Child`** —— 这就是「子嗣加成被完全吃掉」的数学证明。
子嗣让 `Cap_eff` 和 `R` 同乘 `(1+Child)`，分子分母对消；玩家看到的是**上限和灵力数字都变大**，
但突破时间一格不变。`Other` 只乘在分母，所以它是真的加速。

### 2.4 配平系数 K（本表的核心新增）

**定义：**

```
K(L) = 目标本层耗时(L) / 裸公式耗时(L)
裸公式耗时(L) = Base_Exp(L) / [Land × (0.98+0.32Fit) × Fate × spiritRate × k(L)]
```

`K` **不是拍脑袋的常数**，是宪法第二章的逐节点时间表反推出来的。流程：

```
① 取 8 个锚点：L2 60s、L3 180s、L6 1080s、L10 6000s、
             L11 10800s、L14 43200s、L15 86400s、L18 259200s
② 未列出的中间级用几何插值补全（例：L3~L6 三级，公比 (1080/180)^(1/3)=1.817）
③ K = 目标 / 裸公式
④ 有效上限 = Base × K，写进 realm.js（或单独一张 PACE 表）
```

⚠ **方向别写反**：新速度项在低 Fit 时更快（L1: 0.62 → 1.0056），所以 K 要**调高**；

⚠ `K` 是**按基准路线**（默认灵地/Fit、**0 熟练度**）算的。如果改基准路线，K 必须重算。
⚠ 实际熟练度只进 SpeedFit，经 `0.98+0.32Fit` 的窄斜率后约带来 **0~4%** 的加速，属有意保留。

### 4.2 公式

```
L = 12 − S                         // 小循环可用小时（默认 S=2 → 10）
C = 1 + B + 0.75×N                 // 一个周期：练功 1h + 炼体 B×1h + N 个百艺×45m
k = floor(L / C)                   // 完整周期数
r = L − k×C                        // 余时

练功轮次 = k + (r ≥ 1 ? 1 : 0)
炼体轮次 = B=1 ? k + (r−1 ≥ 1 ? 1 : 0) : 0
百艺轮次 = 每项先得 k 次，余时按队列顺序补（先排到的可能 +1）

体力消耗 = S×10 + 练功×3 + 炼体×15 + Σ(百艺轮次×0.75×5或6)
精力变化 = 练功×10 − (炼丹/炼符各30 + 炼阵/炼器各35) + 睡觉×5
互动次数 = min(floor(剩余体力 / 20), 12 / 1h)   // 2026-10-17：15→20，0.5h→1h
睡觉时长 = 12 − 1×互动次数
次日体力 = min(睡觉时长 × 体力上限/4, 体力上限)
```


### 4.5 两条博弈的成立性（这是本 Sheet 最重要的结论）

**博弈 A：白天多干活 → 晚上体力少 → 互动少 → 子嗣少。**
✅ **成立。** 默认 4 次；全天炼体 1 次；四艺术 3 次；巡视拉满 3 次。
互动成本从 15 提到 20 后，同样的白天安排换来的子嗣机会少了约 1/3。

**博弈 B：互动多 → 睡觉少 → 次日体力/精力不满。**
✅ **中期起成立。** 1h/次之后，夜晚只有 12 个互动位：

|---|---|---|---:|---|---:|---:|

| 洗髓圆满 232 | **9** | **3h** | **174（75%）** | 8 | 4h | 232 |
| 超级炼体 24（382） | **12** | **0h** | **0** | 8 | 4h | 382 |

| 选择 | 互动 | 子嗣期望/晚 | 次日体力 |
|---|---:|---:|---:|
| 洗髓·拉满 | 9 | **0.86** | 174（75%） |
| 洗髓·保 4h 睡 | 8 | 0.77 | 232 |
| 超体·拉满 | 12 | **1.15** | 0 |
| 超体·保 4h 睡 | 8 | 0.77 | 382 |

这个比值是否划算，取决于子嗣加成（满配单个 +0.54）值不值 25% 的当天产出 ——
**这是玩家自己的取舍，不是数值 bug。** 如果实测发现大家都选保睡眠，再调高单次怀孕率或降低睡眠惩罚。

**互动成本 / 时长的对比（默认日，白天耗 50；格式 = 互动次数 / 睡觉 / 次日体力）**

| 方案 | 开局 145 | 洗髓圆满 232 | 超级炼体 24（382） |
|---|---|---|---|
| 0.5h + 20（旧方案） | 4 / 10h / 145 | 9 / 7.5h / 232 | 16 / 4h / 382 |
| 0.5h + 25 | 3 / 10.5h / 145 | 7 / 8.5h / 232 | 13 / 5.5h / 382 |
| 0.5h + 30 | 3 / 10.5h / 145 | 6 / 9h / 232 | 11 / 6.5h / 382 |
| **1h + 20（已选，去 30 阈值）** | 4 / 8h / 145 | **9 / 3h / 174** | **12 / 0h / 0** |
| 1h + 25（去 30 阈值） | 3 / 9h / 145 | 7 / 5h / 232 | 12 / 0h / 0 |

**读法：**
- **只加体力成本（15→20/25/30）不会制造睡眠博弈**：开局/洗髓期怎么改都睡 ≥7.5h、次日照样回满；
  只有超级炼体 24 级（382）时，20/次刚好压到 4h，15/次才会 1h 睡到崩。
- **真正制造睡眠博弈的是时长**：互动 0.5h → 1h 后，洗髓期 9 次就是 3h 睡，次日只剩 75% 体力。
- **代码的 30 点阈值会抵消这个效果**：1h+20 在洗髓期会被阈值压到 7 次（5h 睡，回满）。
  所以已拍板**去掉 30 阈值**。
- **成本 25/30 只是让子嗣更少**，不是让睡眠更紧张。要「少子」选 25；要「睡眠博弈」选 1h + 去阈值。

### 5.5 子嗣战力（**2026-10-21 Q3 定稿，唯一口径**）

```
四属性 = 基础值 × 境界系数 × 灵根系数 × 本命系数 × (1 + Σ词条) + 装备面板
战力（展示）= 攻击 × 有效生命 / 100，其中 有效生命 = 气血 × (100 + 防御) / 100
```

> **战力口径（2026-10-23 落地）**：与 `resolveAttack` 的承伤公式同口径（防御 100 = 减伤一半），
> 所以「战力」≈ 这个单位能打出的总伤害。**速度不进战力** —— 它只决定出手顺序，
> 不改变输出量。暴击/连击/闪避那些百分比字段只有灵宠和桂冈带，**没算进去**（估算）。
> 代码：`secretRealm.combatPowerOf`；断言在 `verify-idle` §七。
> **只进展示、不参与任何战斗判定**；编队页的「队伍战力」= 桂冈 + 已选，加总。

> **装备面板**（2026-10-23 P36 第 3 步接入）：攻/防两槽的 `stats` 直接加在最后，
> **不乘境界/灵根/本命**；攻击 → `damage`、速度 → `speed` 平加。
> 子嗣只能穿武器与防具，阶位按**境界段定阶**（练气一/二阶、筑基二/三阶、结丹三/四阶）。

| 项 | 系数 |
|---|---|
| 境界 | **练气一~十层线性 1.0 → 5.0**（每层 +0.444）；**筑基 10.0**；**结丹 30.0**；元婴待 22 级落地再定 |
| 灵根 | 五 0.8 / 四 1.0 / 三 1.2 / 双 1.5 / 单 2.0（无灵根 0.5） |
| 本命 | **tier 1 → 1.0 / 2 → 1.2 / 3 → 1.5 / 4–5 → 2.0**（按物品池基阶） |
| 词条 | **普通 +5% / 稀有 +10% / 传说 +20%**（加算；2026-10-21 P24 拍板回到 Q3 原稿，P23 的「沿用代码 3/7/15」作废） |
| 基础 | 生命 60 / 攻击 6 / 防御 3 / 速度 8 |

**已删除的因子**：品质（low/mid/high/top）、仙龄等级。
仙龄只用于「成年、能否出战、成长曲线」，**不再进战斗属性**。

**桂冈**：属性管线**不变**（现有 `baseAttributes` 10/100/5/10 + 装备 + 灵宠 + 炼体），
只有界面上的「战力」数字按同一公式展示。→ 桂冈与子嗣不能直接比属性，只能比「战力」显示。

### 6.7 预期日产出（调试对照 · P15.6 已落地）

> 调试日志（GM 页 →「调试日志」页签）每天用这张表算一次「计划值」。
> **计划值不是静态数字**：练功小时由当天勾选的巡视 / 炼体 / 百艺决定，

> 本节只记录口径，数值由代码从当前 store 现算。

**时间结构**（与 §4.1 / §4.3 同源；代码里是 `loopStartOf` / `offWorkOf`）：

```
L = 18:00 − max(08:00, 06:00 + S)      // S = 巡视小时；默认 2 → L=10；S=5 → L=7
C = 1 + B + 0.75×N                     // 一个周期：练功 1h + 炼体 B×1h + N 个百艺×45m
k = floor(L / C)，r = L − k×C
任务 i 的轮次 = k + (r ≥ 队列前 i 项时长之和 ? 1 : 0)
```

| 配置 | 练功 | 炼体 | 每种百艺 |
|---|---:|---:|---:|
| 无勾选 | 10 | 0 | 0 |
| 炼器 | 6 | 0 | 5 |
| 炼体 | 5 | 5 | 0 |
| 炼体 + 炼器 | 4 | 3 | 3 |
| 两种百艺 | 4 | 0 | 4 |

**产出计划**：

```
计划灵力 = 日初 spiritPerGameHour × 计划练功轮次
计划修为 = min(60 × 计划练功轮次, 计划灵力 / 打坐成本) × 每次修为 × (1 + 0.3×幸运)
计划体魄 = 同上，用外功等级与计划炼体轮次；内外功按各自可打坐次数分配灵力
计划体力 = S×10 + 练功轮次×3 + 炼体轮次×15 + Σ(百艺轮次×0.75×该艺体力/h)
计划熟练度 = 计划练功小时 / 50 / 100     // 1% / 50 游戏小时 → 0.0002/小时
```

> ✅ **2026-10-19 起代码已按 1%/50h 返工**（`0.0002/小时`），日志上的「熟练度达成率」
> 应与计划一致（约 100%）。旧版稳定显示 50% 的「设计 vs 代码」差已关闭。

>
> ⚠ §6.2 的「每日灵力 / 每日修为」是**设计目标**（Sheet 2 的 `R(L) / e(L)` 口径），
> 与当前代码的 `spiritPerGameHour × 练功小时` 不是同一套数。调试日志一律按**代码现值**算计划，
> 避免日志自己变成第二个真源 —— 两边对不上是已知的返工项，不是日志算错。
>
> ⚠ **体力计划只算白天**（巡视 + 练功 + 炼体 + 百艺），不含晚间互动 ——
> 互动次数本身取决于剩余体力，算进去会变成循环定义。实际值包含互动消耗，所以会略高于计划。
