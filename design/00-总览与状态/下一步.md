P10 — 桂冈的一天（日常循环主界面）

**✅ v1 已落地（2026-10-17）** —— 完整方案见
[`20-系统设计/日常循环.md`](../20-系统设计/日常循环.md)，
睡觉细则见同文 §4.3。

**代码**：主界面已替换首页 `/`（`src/views/Day.vue`），纯函数在 `src/plugins/dayLoop.js`、
store 在 `src/stores/modules/dayLoop.js`，断言在 `scripts/verify-dayloop.mjs`（77 条）。
实现说明与踩坑记在 `CLAUDE.md` 的「桂冈的一天」一节。

**v1 的范围**（三处刻意偏离设计，都写在 `CLAUDE.md` 里）：
巡视乡间真占时间、真扣体力但**无产出**（模块四未上线）；**百艺只有灰槽位**（模块七未上线）；
**精力恒满**（没有东西消耗它）。另外为了配合，时钟放慢了 4 倍
（`SECONDS_PER_GAME_HOUR` 1 → 0.25，一个游戏天 ≈ 1.6 现实分钟），孕育随之 270 → 90 游戏天。

已定的形态：晨起 6:00 → 巡视（1~5h）→ 小循环（8:00~18:00，练功/炼体/百艺）→ 妻妾互动 → 睡觉 →
次日 6:00。**双资源**：精力（100，百艺消耗，打坐 +10/h）与体力（145 起，所有活动消耗，睡觉恢复）。
小循环按勾选的百艺生成队列，勾得越多、练功轮次越少。

把桂冈的日常做成一个**可自动循环的主界面**，而不是让玩家在几个页面之间来回切换：

```
建设乡间 → 练功 → 炼器（或其他生产）→ 回到建设 → …循环… → 下班 → 妻妾互动
```

| 事项 | 说明 |
| --- | --- |
| 循环调度 | 桂冈在**一个默认界面**里按顺序做这些事，玩家看着它跑 |
| 环节来源 | 建设乡间 ← 模块四（封地经营）· 练功 ← 模块一（✅ 已有）· 炼器与生产 ← 模块七（百艺科技）· 妻妾互动 ← 模块二（✅ 已有） |
| 下班 | 一天的结束。之后接妻妾互动（模块二的晚间，✅ 已有），形成完整的一天 |
| 手动接管 | 玩家随时可以打断循环、插队做别的事（具体形式待定） |

**⚠ 这条待办最大的意义不是它本身，而是它会反过来改变 P3 / P9 的形态。**

如果「建设乡间」和「炼器」最终只是「桂冈的一天」里的两个环节，那它们就**不该**各自做成一个
需要玩家切过去操作、切回来再继续的独立页面 —— 那正是这条待办要消灭的东西。

所以：**动手做 P3（封地经营）之前，先把这件事想清楚** —— 封地经营的入口到底是
「一个独立的管理页」还是「主界面里的一环」。这决定了 P3 的 UI 该怎么切。

**✅ 2026-10-16 已对齐**：新方案 §十一「UI 切分」把界线画死了 ——
**观战型**（巡视、练功、百艺、妻妾互动）放主界面循环，**配置型**（封地建筑、徭役、同参/功法切换、
配方管理）放独立页面，**结果型**（战报、事件卡、突破结果）走弹窗。
也就是说：**封地经营的「巡视乡间」是循环的第一环，不需要独立页面；但建筑/徭役的配置面仍需独立页面。**

> 与 P8（UI/UX 整合）的关系：P8 原本写的是「导航扩展：加入内宅、子嗣、封地、任务…」，
> 也就是**按模块拆页**。P10 的方向与之相反 —— 主线日常收进一个界面，独立页面留给
> 真正需要停下来配置的东西（背包、抽奖这类）。两者要在 P8 之前对齐。

P11 — 开局的盾牌与野猪应该做成装备和灵宠

**✅ 已定（2026-10-16）方案 C** —— 见
[`10-模块设计/模块一-修行与突破.md`](../10-模块设计/模块一-修行与突破.md) §9.4。

结论一句话：**不新建物品池，直接改现有池子** —— 灵宠池/灵草池加 `category`/`series`/`tier` 三个字段，
装备改成「普通生成 + 特殊固定」混合制，**删掉 `FATE_ITEMS` 独立表**，同参改为从池子里按
`series`/`category` 筛选、亲和度动态算。同一件物品可以装备、可以出战、可以当同参。
（亲和度的具体档位见 [`模块一`](../10-模块设计/模块一-修行与突破.md) §4.3。）

下面是当初记录的现象，留作背景：

**现象**：桂冈开局「送」的两样东西，现在被建模成了**契合度系统里的「同参」**，
而它们在小说里明明是一件**装备**和一只**灵宠**：

| 小说里的东西 | 现在的 id / 位置 | 现在的建模 | 应该是什么 |
| --- | --- | --- | --- |
| 饕餮纹风磨铜镶青金石玉盾 | `taotie_shield`（`cultivationData.js:128`） | **同参**（`FATE_ITEMS`），且是开局默认主同参（`:289`） | **装备**（盾牌，防具） |
| 乌鬣猪妖 | `wu_li_zhu_yao`（`cultivationData.js:138`） | **同参**（`FATE_ITEMS`），描述写「桂冈**本命**刃背乌鬣猪的活体」 | **灵宠**（可出战） |
| 刃背乌鬣猪 | `dao_back_boar`（`:256`） | **本命** + 本命之物（`:264`） | 本命（这个没问题）／它的「活体」才是灵宠 |

**问题不在数值，在「同一批小说物件被两套系统各记了一半」**：

- 游戏**已经有**完整的装备系统（`attributes.js` 的 `equippedArtifacts`，13 个部位）
  和灵宠系统（`pets.js`，可出战、可升级升星），但**里面一件小说里的东西都没有** ——
  现在抽奖抽到的装备/灵宠全是开源项目遗留的通用货（青玉剑之类，见 P9 要对齐的那批）。
- 而小说里真正有分量、有名字的那几件（盾、猪妖、玉牌、鬣猪），却被抽象成了
  「同参 / 本命」这种**只有契合度系数、没有任何实体行为**的数据。

**要定的是**：这些物件到底是**契合度侧**的（同参/本命，影响修行速度），
还是**装备/灵宠侧**的（影响战斗属性），还是**两边都要**（同一件东西在两个系统里各有一半作用）。
如果是两边都要，就得定清楚**它们之间怎么关联**（比如：装备了某件法器 → 同时充当它的同参？）。

> ⚠ 别在没定这个之前继续往 `FATE_ITEMS` 里加东西，也别急着把小说物品塞进抽奖池 ——
> 两边都会白做。这条实际上会影响 P9（百艺科技对齐）的整个方向。
>
> 相关：模块四（封地经营）与模块五（任务战斗）是唯一会真正用到装备/灵宠数值的地方，
> 所以在做它们之前定下来最省事。
