## P58 — 性能批（2026-10-29 **✅ 已落地**）

**唯一目的**：把「时钟在走 = 主线程 100%」压到可忽略，为 P55-b 的 24 tick/秒 立基线。
**只做纯优化**：功能项（待办 #1 灵兽流水 / #2 灵宠品阶）另立小快修批，不混进来。

### 实测基线（同机同档，`scripts/perf-probe.mjs`）

| 页面 | 时钟 | fps | 脚本 ms/s | 长任务最长 |
|---|---|---|---|---|
| 主界面 | 走 | **1.7** | 994 | 1,027ms |
| 内宅 | 走 | **1.8** | 1,768 | 1,203ms |
| 探索 | 走 | 0.8 | 994 | 2,945ms |
| 封地 | 走 | 1.2 | 999 | 2,977ms |
| 秘境 | 走 | 1.0 | 950 | 1,108ms |
| 背包 / 修行 / 坊市 | **暂停** | 60.6 | 1.4~1.5 | 0 |

暂停页装着同一份 4.96MB 状态却是 60 帧 ⇒ **不是响应式渲染的锅，是 tick 里的落盘**。

### 热点（CPU profile，主界面 6s）

`encryptData` 20.7% + `stringify` 18.3% + AES 内部 36.9% + MD5 6.5% ≈ **80%**；
其次 Vue 的 `get`/`ownKeys` 5.1%（直接序列化响应式代理的额外开销）。

### 落盘微基准（明文 4.96MB）

```
stringify(代理) 275.2ms   stringify(toRaw) 61.1ms
encrypt(代理)   976.0ms   encrypt(toRaw)  713.0ms
```

### 措施（四项，全部落地）

1. **`saveData` 先 `toRaw` 再序列化** —— 976→713ms（−27%），零风险。
2. **落盘节流**：脏检查 + 最长 5 秒一次；页面隐藏 / 关键操作立即存。
   代价：`lastOnlineRealMs` 随落盘走 ⇒ 离线时长最多少算 5 秒（可忽略）。
3. **修内宅页每秒存两次**（实测 存盘/s = 2.0）。
4. **换 WebCrypto AES-GCM**（用户拍板）：纯 JS 的 crypto-js 在 5MB 上要 650ms，
   原生实现约 20ms。需要**存档密文格式版本 + 迁移**（旧档仍用 crypto-js 解），
   且 `saveData` 全链路 async 化要逐处核对。

### 落地记录（2026-10-29）

- **新增 `src/plugins/saveThrottle.js`**（纯逻辑 + 注入时钟）：`markDirty` 只标脏，
  窗口（`SAVE_INTERVAL_MS = 5000`）内排一个定时器，到点写一次；并发写合并成一次；
  写失败保持脏、下个窗口自动重试。`persistence.saveData` 变成「标脏 + 按窗口决定」，
  新增 `flushSave()` 与 `persistSnapshot()`（`toRaw($state)` → stringify → 加密 → IDB）。
- **措施 ③ 的根因不是「内宅特供」**：练功那一片 tick 里 `gainSpirit` 存一次、
  `meditateInSlice → cultivate` 又存一次 ⇒ **练功时段全仓都是 2 次/秒**，
  只是那一轮采样恰好停在内宅。现在两次都只是「标脏」，实测 **0.2 次/秒**。
- **必须 `force` 的六类出口**（漏一处就是丢档或白送离线收益）：
  `App.vue` 的 pagehide / visibilitychange（**状态没变也要写**，否则暂停页挂半小时
  再关页，那半小时会被当成离线时间重算）、读档路径上的迁移与离线结算、导出存档前、
  清档后首次落盘。
- **加密换 WebCrypto AES-GCM**：新密文 `vux2:` + base64(iv12 ‖ 密文+tag)，
  密钥 = PBKDF2-SHA256(口令 `vue-idle-xiuxian`, 固定盐, 120k 次，**一会话只派生一次**，CryptoKey 缓存)。
  老档（CryptoJS base64、无前缀）**只读不写**，读到后下一次落盘自动写成新格式 ⇒
  **不升 `SAVE_VERSION`**（换加密是外层包装，升版反而清档）。`crypto.subtle` 只在安全上下文
  存在（https / localhost），拿不到时退回 CryptoJS —— 慢，但不会写坏档。
- **async 化的落点**：`encryptData` / `decryptData` 都变 async，全仓只有 `persistence.js`
  一个消费者（`initializePlayer` 里的解密加 `await`），其余 130+ 处仍调 `saveData()`。
  `scripts/inspect-save.mjs` 改成**直接 import `crypto.js`**（两种格式它自己判），
  `scripts/perf-probe.mjs` 的落盘微基准跟着 `await`。
- **实测（同一份真档 · `scripts/perf-probe.mjs` · 先做 P57 迁移到 2.06MB 明文）**：

  | 页面 | 时钟 | fps 前 → 后 | 脚本 ms/s 前 → 后 | 存盘/s |
  |---|---|---|---|---|
  | 主界面 | 走 | 1.7 → **59.2** | 994 → **3.3** | 1.0 → **0.2** |
  | 内宅 | 走 | 1.8 → **55.4** | 1,768 → **2.1** | 2.0 → **0.2** |
  | 探索 | 走 | 0.8 → **59.3** | 994 → **2.4** | 0.2 |
  | 封地 | 走 | 1.2 → **59.2** | 999 → **4.9** | 0.2 |
  | 秘境 | 走 | 1.0 → **56.2** | 950 → **2.7** | 0.2 |
  | 背包 / 修行 / 坊市 | 暂停 | 60.6 → 58.4~60.9 | 1.4 → 1.3 | 0 |

  单次落盘：`stringify(toRaw)` 91ms + 加密 ~40ms（**加密从 650~976ms 降到 40ms**）；
  节流后每 5 秒一次 ≈ 总任务 3.4%，仍有 2 条 ~170ms 长任务（内宅 / 秘境量到 12 条，
  是 buff 倒计时 rAF 与 2,800 节点渲染，**不是落盘**）。
- **验证 2028/2028**（1987 + 41 条加密/节流断言 `scripts/verify-persist.mjs`）。
- **还有一条已知代价**（登记 R29）：崩溃/强杀时最多丢最后 5 秒进度；
  正常关页有 pagehide 强制落盘兜底。

### 未定性项（2026-10-29 P57 之后已消解）

内宅页 JS 堆曾涨到 **566MB**（其余页 200~300MB）。P57 落地后同一份档实测

**不是泄漏**。P58 只管把剩下的 400ms/s 压下去。

- 提纯后 `quality` 由新数量派生（见 (c)），所以不需要额外处理。

#### (c) 口径变更：品质降级为「灵根数量的派生标签」

**这是本次最重要的结构变更**，先于 (a) 落地。

- 现在：`rollQuality` 先掷品质（下/中/上/极），`rollRootCount` 再按品质派生数量
  （下 5 / 中 4或3 / 上 2 / 极 1）。
- 改成：**先掷灵根数量**（分布沿用现有概率：5 灵根 60%、4/3 灵根 25%〔4:3 = 6:4〕、
  2 灵根 12%、1 灵根 3%），再按数量派生叫法：
  `5 → 下品、4/3 → 中品、2 → 上品、1 → 极品`。
- `quality` 字段**保留**（存档兼容、本命池、秘境 `qualityCoef`、词表都还按它取），
  但它**不再是独立随机量**，而是 `qualityOfRootCount(rootCount)` 的派生值。
  改数量 = 自动改品质，不需要同步维护两个字段。
- 好处：洗命、提纯、配偶生成都只需要操作「几灵根」这一个真源，
  不会再出现「下品单灵根」这种自相矛盾的状态。

### P15.7 【待检讨】灵地契合是否应该只影响门槛、不影响速度

> **2026-10-18 用户意见：先维持现状，以后再检讨。**

**现状（设计与代码一致）**：换灵地有三条影响通道 ——
1. **品阶 → 基础产出**：直接乘进 `spiritPerGameHour`；
2. **灵地契合 → 综合契合度**：`功法 × 同参 × 灵地`，再经速度项 `0.98 + 0.32×Fit` 影响速度；
3. **综合契合度 + 品阶 → 突破门槛**：两者都参与判定。

**体感问题**：速度项对灵地契合的权重很小（0.32，且 Fit 本身是小数），
灵地契合从 1.0 掉到 0.2，速度项只从 1.0056 → 0.9851（约 −2%）；
而升品阶带来的基础产出提升（如 1.5 → 2.0）远大于它。所以玩家会觉得
「契合度掉了，但速度没掉」，实际公式里那一项是在扣的。

**要检讨的问题**：是否把**灵地契合**从速度公式里剔除，只留作门槛判定？
- 改法：速度项改用「功法 × 同参」算 Fit；灵地契合只进 `overallHarmony` 的门槛判定。
- 好处：换灵地只为突破服务，不会偷偷拖慢日常挂机；灵地的惩罚更直观（卡门槛）。
- 代价：会改《模块一》§3.3/§4.1/§5.1、《数值真值表》§2.2/§3.4/§7.6 的验算，
  以及 `verify-harmony.mjs` 里「速度项按旧曲线重标定」那组断言。
- 关联待拍板：《数值真值表》§7.6「筑基/结丹槛的灵地容错」还没解决
  （结丹槛 0.80 要求灵地 = 1.000，实际几乎只能完美匹配）。

**结论**：暂不改代码。等《数值真值表》§7.6 一起检讨。

> 来源：P33 查「洗练石留不留」时实测发现。**不是设计问题，是上游遗留代码的 bug。**

**实测证据**（2026-10-22 一次性探针，各 300 次）：

| 装备形状 | 结果 |
|---|---|
| 灵器（`type` = 中文「剑」等） | **132/300 抛 `TypeError: Cannot read properties of undefined (reading 'filter')`** |

**根因**

1. `equipment.js` 的 `reforgeEquipment` 用 `equipment.type` 查 `reforgeableStats`，

2. 属性替换是「先删旧键、再加新键」，遇到可用属性为空或重复时会缩表，
   再撞上「属性数量必须相等」的兜底校验 → 明明能成功的洗练被判失败。
3. `scripts/verify-*.mjs` 里**一条洗练断言都没有**。

- 洗练是否消耗 10 颗、±30% 重掷这套数值要不要保留（目前**没有任何设计真源**，是上游默认值）。

| 6 | 起始层 | 整备页二选一：**第 1 层**（默认，机缘拿满）/ **接着上次打**（`min(最高层+1, 50)`） | `clampStartFloor` / `startFloorLimitOf` |
| 7 | 起始层的时间成本 | 只算**本趟实际走过的那一段**：`ceil(max(0, 已通 Boss 层 − (起点−1)) / 10)`；起点 1 与旧公式完全等价 | `timeCostDaysOf(层数, 起点)` |

### 为什么「从第一层打」本来就有，仍然要做

原实现每趟都写死从第 1 层开始，所以用户想要的**不是**「补上从 1 层开始」，
而是「**别强迫我每次从头看动画**」的另一半：给一个跳过已通 Boss 层的选项，
同时保住「从第 1 层蹭满机缘」这条路。跳过会少拿机缘（每 5 层一次），时间按实际段算，
所以两条路各有取舍，不是纯优化。

### 产出影响

- **收益增加**：队伍不再因为一个脆皮而提前回家 ⇒ 趟均层数上浮 ⇒ 宝匣 / 灵石 / 首破变多。
  已登记《产出登记表》**R21**，门槛重算等实测数据（是真机曲线，不是纸上公式）。
- 起始层选项本身**不改变效率**：每 5 层 1 宝匣 + 每 10 层 1 天 ⇒ 恒 2 宝匣/天，
  跳过只是把同一段路走短、现实主义时间。
