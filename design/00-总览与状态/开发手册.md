## 二、代码约定

### Store 是有意拆成「单 store + 多模块文件」的

`src/stores/player.js` 只有一个 `defineStore`，`src/stores/modules/index.js` 用
`Object.assign` 把各模块扁平合并。

- `state` **必须是工厂函数**（`$reset` 依赖重新调用）。没有 state 导出的模块（如 `clock.js`）会被 filter 掉。
- `actions` / `getters` **必须用方法简写** `foo() {}`，**不能用箭头函数** —— 合并后 `this`
  由 Pinia 绑定到 store 实例，跨模块走 `this.xxx()`。
- 模块内**禁止** `import { usePlayerStore }`（循环依赖）。
- DEV 下只检查 getter/action 重名，**不检查 state 键重名** —— 新增 state 时自己注意。
- `modules/debug.js`（P15.6 调试日志）**刻意没有 state**：日志、环形缓冲与目录句柄都放在
  模块闭包里（与 `gameClock` 同理）。`saveData()` 不会带上它们，`$reset()` 也清不掉 ——
  GM 页的「重置数据」显式调 `debugResetAll()`。

### 纯函数层与运行时层分开

`src/plugins/*.js` 都是**无副作用纯函数**，刻意给相对 import 加了 `.js` 后缀，好让 node
直接加载跑断言。`src/plugins/gameClock.js` 的计时器句柄与钩子表放在**模块作用域闭包**里，
只把 `clockState` 这个 reactive 影子对象透给 UI —— 进 Pinia state 会被序列化进存档，
且 `$reset()` 清不掉旧 timer。

### 灵力/秒只有一个真源

`practice.js` 的 `spiritPerSecond` getter。UI 和实得都读它 —— 旧版页面里另拼了一份公式
且漏了因子，两处口径对不上。

### 页面布局只用「分区框」一种写法

一页里「一块完整信息 = 一个 `<section class="zone">`」，样式 token、结构、8 条坑和迁移清单
见 **[UI 视觉规范](../20-系统设计/UI%20视觉规范.md)**。要点先记三条：

- 区间距用普通 flex + `gap`，**不要** `n-space vertical`（0 → N 动态子节点会重复渲染）；
- 区底色/边框用 `color-mix(in srgb, var(--n-text-color) N%, transparent)`，
  **别写死 `rgba(255,255,255,…)`**（亮色主题下隐形）；
- 区框里不要再套带边框的 `n-card`（双层框），子块一律 `:bordered="false"`。

### 读文件 / 跑命令：一批并行，别一串串行

会话成本 ≈ 往返次数 × 每次重读的上下文，所以**「一轮里塞进多少工具」比「工具返回多大」重要得多**
（2026-10-22 实测 bebed01a：268 往返 / 265 工具，工具/往返 **0.99**，5.61 成本，
其中 84% 是缓存读 —— 一个工具一往返，串得很干净）。

- 相互独立的读/查/命令**放进同一条消息**并行发；串行发会把往返翻倍。
- 大文件用 `Read(offset, limit)` 只读需要的段，别整份读（`Dungeon.vue` 一次读 29.6k 就是反例）。
- **别用 `sed -n` + `echo "=== … ==="` 拼多段读**冒充一次读文件：它是多条命令、多轮往返，
  返回还不受 Read 的截断保护。要拼就是一条 `Read` 一条命令。
- 命令别接 `| tail` / `;` / `&&` / `$()`：既废掉白名单（见根 `CLAUDE.md`），又白多一轮。
- 自查指标：`npm run token-report` 的**「工具/往返」**列 —— **≈1 = 全串行，≥2 = 真的并行了**。
  注意日志把同一次请求按内容块写了多条（每块都带完整 usage），脚本已按 `requestRef` 去重；
  早于 2.1.3xx 的会话没有这个字段，那部分数字仍是翻倍的，别拿旧会话横向比。

## 四、命名约定：精力 vs 体力

P10 的双资源设计跟代码里现有的名字打过一架，对应关系已钉死（详见《日常循环》§十四）：

| 新设计 | 代码现状 | 关系 |
|---|---|---|
| **精力**（上限 100；百艺消耗；打坐 +10/h、睡觉 +5/h） | `dayLoop.focus` | 全新资源 |
| **体力**（145 起；所有活动消耗；睡觉恢复） | `innerCourt.energy`（上限随炼体涨） | **同一个东西**，都是「互动 −15」那个节流阀 |

**定死：**

1. **`innerCourt.energy` 语义上就是新「体力」** —— 值不动、存档不动，只改中文标签和上限。
   **别再叫它精力。**
2. **新「精力」另开字段 `focus`**，**不要复用 `energy`**。
3. **精力上限恒 100，不随炼体涨**；要涨的是**体力上限** ——
   `145 + 外功加成`（炼体 +3/级、锻骨 +6/级、洗髓 +9/级、超级炼体 +25/级 → 172 / 196 / 232 / 380+）。
4. 精力耗尽不是「回满」—— 是**打坐一轮（1 小时，+10）后放弃当天剩余安排、提前下班**。

### 流水账的格式（**结算结果**）

每个环节**跑完记一条**，带上该环节实际生效的结算：

```
08:00  巡视乡间 2 小时（封地未开放，无产出） · 体力 -20
09:00  练功 1 小时 · 灵力 +12 · 修为 +1 · 体力 -3
12:00  妻妾互动 4 位 · 有喜 2 位
06:00  睡觉 12 小时 · 体力 +50
06:00  ── 第 2 日 ──
```

四条不能忘：

1. **累加器住在 state 里**（`createDayState` 的 `settle`）。一个练功轮 = 1 游戏小时 = 4 个 tick，
   而 `stepDay` **每 tick 只被调用一次** —— 累加器只要放在任何函数体里（store 的或 `stepDay` 的）
   都会每 tick 清零，把一轮报成「0.25 小时」。**这个 bug 连踩两次。**
2. **报的是「实际生效量」**（夹过上下限之后的），不是原始量。睡觉原始恢复是 9×36.25 ≈ 326，
   但体力上限只有 145 —— 报 326 就是骗人。
3. **灵力报的是产出量**，不是余额变化 —— 它紧接着就被打坐花掉了，看余额永远是 0。
   同理「修为」取的是掷出来的收益（含 30% 翻倍），不是余额差（突破会把余额清零）。
4. **写入顺序 = 事件发生的先后**，不是代码顺手的顺序：环节 → 突破 → 互动 → 睡觉 → 换日分隔。
   `advanceDayLoop` 里 `pending`（互动）必须**晚于** `completions`（刚做完的环节）处理；
   换日分隔同理**必须最后插**，否则会夹在「妻妾互动」和「睡觉」之间。

> 另外两类**不进**流水：`idle`（空转，没有结算）与 `evening`（已由 `runDayEvening`
> 自己写简报）。不然会打印出「evening 0 分」这种内部术语。

### 五条最容易踩的

1. **`advanceDayLoop` 取代了原来 tick 里直接调 `gainSpirit` 的那一行**。灵力/熟练度现在
   **只在练功切片**产出。**练功切片还要顺带「打坐」**（`meditateInSlice`）—— 把灵力换成**修为**。
   设计里这个环节的名字就是「练功（打坐）」：产灵力和打坐是同一小时里的两件事。
   v1 首版漏了这一步，症状是**灵力一直堆着、修为永远是 0**。
2. **`spiritPerSecond` 已改名 `spiritPerGameHour`，单位从现实秒变成游戏小时**。
   它挂在 tick 上时是「每 tick 加常数」，时钟一放慢就会每游戏天白送 4 倍。
3. **`energy` 这个字段名的语义是「体力」**（历史包袱，存档键不能动）。新的「精力」是
   `dayLoop.focus`。别混。
4. **`advanceInnerCourtDay` 里那行「每日回满体力」已删除**。体力靠睡觉回补（上限/4 每小时）。
   加回去会让「白天多干活 → 晚上互动少」这条取舍直接失效。
5. **工作日以 06:00 为界**（`dayLoop.workDayOf`），与 innerCourt 的 `gameDayOf`（00:00 界）
   **刻意不同名**。混用会让「今日安排」跨午夜时错位。

### v1 的边界（**都不是 bug**）

- **巡视乡间**（属模块四）**真占时间、真扣体力，但无产出** —— 日志写「封地未开放，无产出」。
  这是故意的：留着它，「调整巡视时长」这个滑块才是真的，设计 §四 的体力取舍也才成立。
- **百艺**只开放**炼器**（P12.4，默认勾选）；炼丹/炼符/炼阵仍是数据位。炼器 45 分钟/轮、
  体力 −6/h、精力 −35/天（每艺每天一次），每轮随机产一件金系一阶装备进背包。
- **精力不再恒满** —— 炼器是它的第一个消费口；耗尽后自动补一轮练功再提前下班。
- **掉落的装备固定一阶凡品** —— 「炼器等级 → 产物等级」还没做（P15.8）。
- **`src/views/Home.vue` 已不被路由引用**（主界面占了 `/`），文件先留着。

### 玩家介入（主界面上的按钮）

| 按钮 | 作用 |
|---|---|
| 巡视时长滑杆（1~5h） | 明天下班前后的巡视长度。当天已跑过的不改 |
| 勾选炼体 | 当天即生效：小循环变成练功/炼体交替，练功轮次减半 |
| 打断循环 | 做完手上这轮就下班 |
| 今晚不互动 | 跳过晚间，直接睡（换更多睡眠） |

> **睡觉是「加速播放」，不是按钮、也不再瞬间跳过。**
> `advanceDayLoop` 一进入 `sleep` 就调 `startSleepFastForward()`，给 gameClock 加一个倍率，
> 让整段睡眠在约 **3 现实秒**（≈ 一轮炼器）里走完。
> ⚠ 倍率与限流（`setTimeScale` / `setAdvanceLimit`）活在 gameClock 的模块闭包里，
> `$reset()` 清不掉。**离开睡觉、离开镇守、`resetDayLoop()` 都必须 `stopSleepFastForward()`**，
> 否则会把探索的时间一起加速。
> ⚠ `advanceLimit` 是防后台节流的保险丝：5 秒 tick 在 12 倍速下会冲过天亮。
> ⚠ 不再用 `skipTo()` 跳睡 —— `hour/day` 边界现在由正常 tick 推进补触发。

## 八、坑（踩过的，别重复踩）

1. **`modules/index.js` 的 state 兜底。** 旧代码 `m[field] || {}` 对没有 `state` 导出的模块兜底成 `{}`，
   而 `{}()` 抛 `factory is not a function`，**整个 store 构建崩**。已修成
   `.filter(f => typeof f === 'function')`。

2. **单位换算藏在常量里。** 旧版熟练度写 `hours × 0.01`，而 `hours` 的分母是
   `secondsPerGameHour: 2` —— 实际 40 现实秒就顶满 20%，比设计快 **100 倍**。
   现在 `hoursFromSeconds` 是纯换算 `s / 3600`。

3. **两个并行计时器。** 「每 tick 给灵力」一度有两个独立 `setInterval` 在跑
   （`App.vue` 的 worker + `Cultivation.vue` 本地定时器），互不知晓，收益翻倍。
   现在**只有一个** `gameClock` 的 interval，别再加第二个。

4. **bat 文件的两个陷阱。**
   - `chcp 65001` + UTF-8 的 bat **在中文 Windows 上会坏**：cmd 按**字节偏移**读批处理文件，
     执行中途切码页会让后续行解析错位。要么存成 **GBK**，要么内容保持**纯 ASCII**（当前选择）。
   - **必须 CRLF 行尾**。`if not exist (...)` 这种括号块在 LF 下最容易解析失败。

5. **`npm run build` 会覆盖 `docs/`**，而 `docs/` 是**已提交的部署产物**。
   它不会自动跟着代码更新 —— **部署前必须重建**。（`terser` 现在已在 devDependencies 里。）
   2026-10-15 曾留过一份「修 bug 之前构建的、启动即崩的」产物，别重演。

6. **中文路径 + bash 传给 cmd 不可靠。** `cmd //c <中文路径>`、`git mv` 碰到中文路径都可能失败
   （cmd 拿不到正确的 cwd）。本仓库路径是 `.../Project/多子多福`。
   验证 bat 之类的东西时，把它复制到 ASCII 路径下跑。

7. **`git clean -fd` 会被权限拦。** 破坏性 git 命令要用户自己跑（用 `! 命令` 前缀）或明确点名目标。

8. **设计文档的验算表会算错。** 《灵气系统》§7.3 有两行加错了、§4.3 例子的「一阶」用了一阶下品的值。
   所以有了 `npm run verify` —— **改完数值一定跑**，里面还有几条**反向断言**
   （如「开局 50.25% 必须被练气三层拦住」），专门证明门槛不是装饰。

9. **「设计完整 ≠ 可玩」。** §7.2 那张成长路径表假设兽/器功法、三阶同参、第二件本命物**都已到手**，
   而这些在游戏里一条获取途径都没有。做新模块时先查一遍「它依赖的东西存在吗」。

10. **两种暂停会互踩。** `router.afterEach → syncClockPause` 在离开暂停页时会**无条件
    `resume()`**。若「事件暂停」（诞生弹窗）与「路由暂停」共用 `clockState.state` 一个字段，
    玩家在弹窗开着时点任何导航，事件暂停就被踩掉。现在 `gameClock.js` 用的是**多持有者模型**
    （事件持有者 `Set` + 路由持有者，由 `applyState()` 派生状态），**bug 由结构消除**。
    不要在 `syncClockPause` 里加 `if (state === 'paused_event') return` 那种特判。
    ⚠ 持有者活在模块闭包里，**`$reset()` 清不掉**，所以 `persistence.initializePlayer()`
    必须调 `clearEventPauses()` 后按存档重放。

11. **不挂在 `tick` 上的结算必须自己 `saveData()`。** 存档的每秒落盘点只有
    `core.gainSpirit` 这一个（挂在 `tick` 上）。凡是发生在**没有 tick 的时刻**的结算
    都得自己落盘，目前有两处：内宅的每日推进与 `interactEvening`。
    漏掉 `saveData()`，结果**永远不会进存档，刷新即丢**。

12. **「绝对时刻」和「起床后几小时」是两回事。** `dayLoop.js` 的 `WAKE_HOUR = 6` /
    `LOOP_START_HOUR = 8` / `OFF_WORK_HOUR = 18` 是**一天里的钟点**，而 `dayStartSeconds`
    指向的是 06:00。直接写 `dayStart + LOOP_START_HOUR * HOUR` 就变成「起床后 8 小时」= **14:00**。
    这个 bug 最阴的地方是**默认参数下被巧合掩盖**：14:00→24:00 恰好也是 10 小时练功，
    只有把巡视拉到 5 小时才露馅。
    → 换算必须走 `loopStartOf()` / `offWorkOf()`。

13. **工作日以 06:00 为界 ⇒ 游戏时间 0（新档起点）算出来是「第 -1 个工作日」。**
    `workDayOf(0)` = -1、`dayStartOf(0)` = -64800，第一次推进会把整个日程快进一遍。
    `createDayState` 里的 `Math.max(..., 0)` 就是夹这个的，**别删**。

14. **Pinia 的 getter 是 computed 属性，不是方法 —— 别写成 `this.xxx()`。**
    `practice.js` 的 `bestImprovement` 里写过 `this.dimensionBreakdown()`，于是去「调用一个数组」，
    抛 `is not a function`。它只在 `Cultivation.vue` 的 `v-if="blockedByGate"` 下求值，
    第一次触发是「练气二层圆满」，那一刻修炼页整页白屏，现象像「路由没切过去」。
    → `npm run verify` 有一条**静态扫描**会报这个（`verify-harmony.mjs` 第 9 节）。

    > **通用教训**：只在**罕见状态**下才求值的代码（门槛拦住、首次突破、空列表、上限值……）
    > 最容易带 bug 上线。写这类代码时，要么补断言钉住那个状态，要么放进静态检查。

15. **在 rAF tick 的回调里启动新回放，会被同一 tick 末尾的 `stopLoop()` 取消。**
    `useRealmPlayback.js` 的 Buff 10 秒倒计时到期时，回调里 `autoChooseSecretRealmBuff()`
    + `playFrames()` → `load()` 会排一个新的 `requestAnimationFrame`；但倒计时分支结束后
    `active` 仍是 false，tick 末尾 `else stopLoop()` 把刚排的 rAF 取消。
    症状：`frames` 已载入、`playing=true`，但永远不动；战况卡显示「等待开战……」。
    → 回调之后必须重新判断 `playing.value || countdownCb`，有就 `active = true`。

16. **`n-space vertical` 包动态列表时会把子节点重复渲染。**
    2026-10-20：子嗣页从「空列表」变成「有数据」时，工具栏（筛选器 + 人数）在 DOM 里
    出现了 **4 份**，其中 3 份挤在统计条和「各代存活」之间。模板只写了一次，编译产物也只创建一次；
    换成普通 `<div class="offspring-stack">` 后立刻恢复成 1 份。
    → 页面里**动态增删内容**的纵向容器优先用 flex div；`n-space` 留给静态/结构稳定的地方。
    排查时先数 DOM 节点（`document.querySelectorAll('.table-toolbar').length`），别只看源码。
