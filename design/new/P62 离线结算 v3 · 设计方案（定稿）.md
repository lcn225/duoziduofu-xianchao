# P62 离线结算 v3 · 设计方案（修订 v3 · 代码核对 + 秘境口径拍板）

## 一句话结论

四步施工：**步骤 1 封地块化（54 → 35~38 秒）→ 步骤 2 活跃索引（→ 22~26 秒）→ 步骤 3 块内批量结算（→ 15~20 秒）→ 步骤 4 探索期望值结算 + 秘境改扫荡口径（两条线各自毫秒级，≤10 秒）**。全部只改「怎么算」不改「算多少」；步骤 1、2 相对**当前离线路径**零精度损失，步骤 3 的近似在 R34 接受范围内，步骤 4 的探索线保留一处已接受近似（重伤养伤），**秘境线改口径后零精度损失**。

> **v2 修订（2026-11-12，按仓库代码逐条核对）**：v1 有四处「想当然」，本版全部以代码为准改掉。
>
> 1. **步骤 2.2 重写**：v1 的「凡人桶块内完全不动、家族工作收尾结清」会**掐断药浴料路**——凡人灵田岗产的是**灵植**、直接进背包，而药浴每天从背包扣灵植（见 2.2）。改为「在岗索引 + 块内每日到货」，只把灵石 / 法器延迟。
> 2. **步骤 3 重写**：v1 的「跨块复用模板」不成立。`applyOfflineDayTemplate` 是**有状态的逐日重放**（每天要 `cultivate`、按轮扣料、推进百艺、跑晚间互动，遇突破即停），没有可跨块复用的纯矩阵。改为「块内 N 天一次性批量结算」；失效条件也从 5 条收敛到 1 条。
> 3. **㉓ 改结论**：叙事**不能抽样**，抽样会丢 autoChoice 奖励、违反「产出期望不变」。改为「奖励并入期望值，文本只做展示」。

>
> **v3 追加（2026-11-12 判定）**：**离线秘境改成「扫荡口径」**——不再续跑当前 run、不再推新层、不写首破、不给 50 层首杀、不消耗消耗品。连带口径见步骤 4.2。

## 现状

- 30,240 天 ÷ 180 天/块 = 168 块（`plugins/offlineSimulation.js:77` `blockDays.core = 180`）。镇守模式每块：日常循环 1 次完整 + 179 次模板重放、内宅 1 次（带 days=180）、封地 180 次逐日、飞鹰门 / 俸禄 / 药浴池各 1 次。
- **家族工作每次全族遍历**（`stores/modules/innerCourt.js:1722`），产出四类：现银 `secular` / 灵石 `spiritual` / **灵植（直接进背包）** / 法器（进背包）。岗位表见 `plugins/innerCourt.js:600-637`（庄头 / 账房 / 商队管事 / 灵田佃农 / 工坊匠人）。
- 内宅每次块结算对全族扫 6 遍；封地每天深拷 + `estateOffspringCount` 全族过滤 + `materialsOf` 全背包过滤。
- 探索：30,240 个窗口逐窗推事件（**叙事已按 `autoChoice` 自动落奖励**，`stores/modules/offline.js:294`）；秘境：**续跑存档里那趟 run，逐趟 × 每趟 10 段战斗**（`stores/modules/offline.js:330-431`），一趟满 50 层 = 5 天。两条线**均未实测**。
- 已接受的精度损失（R34）：诞生 / 寿终按块末、繁育折算、药浴池块末一次、封地仍逐日。
- P62 约束：产出期望不变、现有 **3,439** 条断言不回归、只改离线路径、在线一行不改。

**验收口径（本次更新）**：

## 方案

### 步骤 1：封地块化 + 增量维护（零精度损失）

**1.1 块内逐日推、只写回一次**

- 现状：每天 1 次 `cloneEstate` 深拷（`plugins/estate.js:1101`）+ 1 次 `estate` 写回 + 1 次 `currency` 写回 + 1 次 `saveData`。
- 改后：块首深拷 + normalize 各 1 次（normalize 现在已经是 `ensure:false` 只跑块首，`stores/modules/estate.js:207`）；块内逐日推**原地改同一份 state**；块末一次性写回 `estate` 与 `currency`，`saveData` 1 次。
- 逐日推的逻辑不变（仓满刹车、月税、徭役分配、建设付款照旧按天判）。

**1.2 延迟账户：保持「当天收入次日可用」**

- 块内维护 `available`（今天可用）与 `pending`（今天入账、明天可用）。
- 每天：建设预算从 `available` 扣；当天经营链 / 税收 / **凡人岗位灵石**收入进 `pending`；日末 `available += pending; pending = 0`。
- 块末：`currency.spiritual = available`。
- 与在线逐日完全等价，**零精度损失**（口径 A，你已拍）。

**1.3 两处全量扫描改块首一次 + 增量**

| 扫描                       | 现状                                         | 改后                                       | 精度  |
| ------------------------ | ------------------------------------------ | ---------------------------------------- | --- |
| `estateOffspringCount`   | 每天全族 filter（`stores/modules/estate.js:79`） | 块首算一次；块内按「新生 − 修士死亡」增量维护。凡人寿终按块末判定，块内不减           | 无损  |
| `materialsOf`            | 每天全背包 filter（`plugins/arts.js:637`，由 `stores/modules/estate.js:228` 传 `bagItems` 触发） | 块首扫一次建池（按 type / tier 索引）；块内按乡间百艺消耗扣减 | 无损  |

⚠ **`materialsOf` 的「块内只减不增」只在镇守模式下成立**：探索模式里背包会进料，但探索与封地结算共用 `settleOfflineBlock`，需要按「块内是否可能涨料」二选一实现（见断言清单）。

### 步骤 2：活跃索引（零精度损失）

**2.1 离线开始时一次分桶**

| 桶   | 条件                          | 块内处理                                    |
| --- | --------------------------- | --------------------------------------- |
| 修士桶 | 有灵根 + 未满级                    | 修炼 / 历练 / `preFoundationIds` 只扫它       |
| 历练桶 | 有历练配置 或 养伤中                 | 养伤倒计时只扫它                                |
| 繁育桶 | 男性 + 活着 +（已婚 或 块内可能到青年）     | 繁育只扫它                                   |
| **在岗桶** | **有 `job` 且活着（当前 = 无灵根凡人）** | **家族工作只扫它**；块首建一次，块内成员不变             |
| 凡人桶 | 无灵根 + 活着但无岗                  | 任何日循环扫描都不进（仍参与块末寿终判定）                   |
| 已故桶 | fallen / passed_away        | 任何扫描都不进                                 |

**块间不变量**：桶成员在重放期间不变——离线期间不分配新岗位、不配置新历练、不新增修炼位。唯一变化是繁育桶内产后恢复回桶，仍在桶内处理。

**2.2 凡人产出：在岗索引 + 块内按天到货（v2 重写）**

> v1 的「凡人桶完全不动、收尾一次性结清」不可行：凡人**灵田佃农**产的是**灵植**，直接 `gainItem` 进背包（`stores/modules/innerCourt.js:1776-1783`）；而药浴的合法料源就包含灵植（`plugins/bath.js:29` `BATH_CATEGORIES`），块内每天 `settleBodyRound` 从背包实扣（`stores/modules/bath.js:271`）。凡人岗位整体推到块末 ⇒ 块内第 2~180 天药浴缺料 ⇒ **炼体产出下降**。这既不是「零精度损失」，也和 1.3「块内材料只减不增」自相矛盾。

- **在岗桶在块首建一次**：`{ id, jobId, 四类日产量, 岗位词条加成 }`。块内只遍历它，不再全族 filter。块首对每人做一次 `canDoFamilyJobOf` 与余数账初始化。
- **四类产出的落点分开**：

| 产出          | 落点             | 理由                                 |
| ----------- | -------------- | ---------------------------------- |
| 灵植 `herbs`  | **块内每日入背包**    | 药浴唯一料路，必须按时到货（见上）                  |
| 灵石 `spiritual` | 块内每日进 `pending` | 走 1.2 延迟账户，次日可用                    |
| 现银 `secular`   | 块内每日入账         | 不参与建设预算，无时序依赖                      |
| 法器 `forgeItems` | 块末一次性入背包       | 块内无人消费，推迟无害                        |

- **寿终**：死亡日 = 出生时间 + 寿元 × 365 天。死亡日在块内的，**块内仍计为活着**（与现有 R34 口径一致，不新增近似），块末统一判死、标记 `passed_away`、写流水。块内繁育产生的新凡人寿元 80 岁 ≫ 块长 180 天，块内不可能死。
- **繁育照常块内计算**，块内产生的新子嗣出生即入「新人池」（无岗），零成本。
- **收益**：家族工作成本从 `O(全族 × 天数)` 降到 `O(在岗数 + 天数)`，灵植料路保持逐日精确。
- **断言**：块内药浴吞噬件数不得因离线块化下降（同档同一份档，改造前后对比）。

**2.3 修士寿终仍块内结算**

修士寿元随境界变化（突破会改寿元），不能预计算。修士桶人数少，块内正常判即可。

**2.4 繁育桶预筛边界**

块首预筛时把「未婚但块内可能到青年」的男性也纳入繁育桶，否则块内婚配后的新人无法受孕。具体「青年年龄」与「块内可能到」**交开发组按 `canMarryOf`（`plugins/innerCourt.js:2615`）实现**；方案只要求：块内新发生的婚配，其对象必须在繁育桶里。

### 步骤 3：块内 N 天一次性批量结算（v2 重写）

> v1 的「跨块复用日常循环模板」不成立。块首跑 1 天拿模板**已经落地**（`stores/modules/offline.js:200-216`）；剩下的成本是**块内 179 次逐日重放**。重放不是纯矩阵运算：它每天 `cultivate`、按轮 `settleBodyRound`（实扣背包料）、`advanceArtRound`、`runDayEvening`，且 `this.level` 一变就 `break`（`stores/modules/dayLoop.js:474-501`）。所以不存在「块间不变就复用」的模板。

- **目标**：把 179 次逐日重放压成 1 次「N 天批量」，而不是跨块搬运。
- **四类积分的批量口径**：

| 环节   | 批量写法                                            | 边界          |
| ---- | ----------------------------------------------- | ----------- |
| 修为   | `cultivate(模板修为 × k)`，`k = min(N, 到封顶所需天数)`     | 封顶即停，不溢出    |
| 药浴   | 总轮数 = `k × bodyRounds`，一次结；料不足按料封顶                | 灵植到货曲线由 2.2 提供 |
| 百艺   | `advanceArtRound(kind, 模板工时 × k)`               | 同一配方连续跑     |
| 晚间互动 | `runDayEvening(模板次数 × k, { silent: true })`     | 已支持次数参数     |

- **突破切分**：先算本块能否突破 → 能则按「突破前 k1 天 + 突破后重取模板」切段，与相位分段同构。
- **失效条件只有一条：本块内发生突破。**（v1 列的五条里：「侍妾数变化」不影响 dayLoop——繁育走内宅日结，`advanceDayLoop` 不读侍妾数；「材料耗尽」是**封顶**不是失效；「玩家改配置」离线期间不可能发生；「境界变化」与「突破」是同一条。）
- 剩余成本：168 块 × 1 次批量 ≈ 与当前块首开销同量级。

### 步骤 4：探索期望值结算 + 秘境改扫荡口径（v3）

**4.1 探索线：纯期望值**

| 环节       | 期望值结算                                                           |
| -------- | --------------------------------------------------------------- |
| 事件数量 / 天 | 地图事件触发率 × 天数                                                    |
| 二选一事件    | 两种结果各算期望产出，加权（`runOfflineExplorationSlice` 的 `ctx` 不依赖状态，已确认 ⑲） |
| **叙事事件** | **奖励按 `autoChoice` 的确定性结果并入期望值**（不抽样，见 ㉓）                          |
| 战斗胜率     | 胜率 × 胜产出 + 败率 × 败产出（胜率按境界判定；注意战力随炼体 / 功法在块内变化，需按块首状态取值并在文档写明） |
| 掉落阶      | 按境界段定阶，突破则**分段**结算                                              |
| 重伤养伤     | 重伤概率 × 12 天折算平均损失天数（**有损，已接受 ㉑**，误差 ≤1 天/次）                     |

**4.2 秘境线：改成扫荡口径（v3，用户 2026-11-12 拍板）**

**语义：离线期间的秘境 = 反复执行「扫荡」，不续跑、不推新层。**

- 不再读 `secretRealm.run` 续跑，不再 `buildSecretRealmParty`，不再逐段 `runSegment`。
- 每趟 = `sweepLoot(sweepLimitOf(highestBossCleared), rng, TUNING, difficulty)`，扣 `timeCostDaysOf(cap)` 游戏天（50 层满通 = 5 天/趟）。
- N 天能扫 `floor(N ÷ 每趟天数)` 趟，**余数不结算**（与在线一次一次按完全一致）。
- **不写首破**、**不给 50 层首杀**、**不消耗消耗品、不吃 buff**（与在线扫荡 `startSecretRealmSweep` 同口径）。
- 掉落仍逐趟掷骰（上限约 6,048 趟），成本可忽略 —— **秘境线零精度损失**，不需要期望值结算。
- `cap = 0`（一个 Boss 都没通过）⇒ 离线秘境**不产出**，只推进时间。

**连带变化（必须同步写进文档）**：

| 变化                                        | 说明                                                     |
| ----------------------------------------- | ------------------------------------------------------ |
| 「唯一暂停点 = 子嗣陨落」在秘境离线模式**不再触发**          | 扫荡没有战斗、没有阵亡。`CLAUDE.md` 的离线硬口径要加这个例外               |
| 首破 / 50 层首杀**只能在在线拿到**                    | 挂机拿不到里程碑奖励 —— 这是改口径的直接后果，写进《三大挂机》                       |
| 下线时那趟进行中的 run **冻结**                      | 离线不推进它，上线后原样继续；离线期间按扫荡结算（**默认口径，开发组按此实现**）         |
| 在线「扫荡要求镇守模式」 vs 离线「秘境模式扫荡」**不对称**         | 离线是特殊口径，写进《模块九》，不改在线限制                                 |
| 陨落词条返还 / 英烈祠 / 消耗品三层槽                     | 离线秘境不再产生，相关逻辑可整段删除                                     |

**4.3 两条线共同的边界**

- **探索线**：离线期间若突破境界，期望值按**分段**算（突破前旧段、突破后新段），与镇守的相位分段一致（已确认 ㉒）。
- **秘境线**：扫荡掉落只吃 `difficulty` 与已通关层数，**不随境界变化，因此不需要分段**。
- 验收不再需要秘境真档：按 `timeCostDaysOf` 公式造档即可（㉕ 已结案）。

### 4.4 施工顺序

| 序   | 步骤                 | 预估累计              |
| --- | ------------------ | ----------------- |
| 1   | 封地块化 + 延迟账户 + 两处增量 | 54 → 35~38 秒      |
